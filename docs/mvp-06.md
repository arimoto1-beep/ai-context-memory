# MVP6: Working Memory から正しく忘れる（remove）

## 今回解決したい問題

MVP5 の Working Memory は「追加」と「置き換え」しかできなかった。実際の Claude で次の問題が起きた。

変更前の scope:

- 商用環境を対象とする
- ステージング環境を対象とする
- 開発環境を対象とする

ユーザーが「ステージング環境はやっぱり対象外にします」と入力すると、作業記憶の抽出 AI は削除の手段を持たないため、置き換えで表現した。

```text
[作業記憶] scope: ステージング環境を対象とする → ステージング環境は対象外とする
```

その結果、scope に「ステージング環境は対象外とする」という否定情報が残った。回答用の AI はこのターンでは正しく「対象は2環境」と理解したが、現在状態としての scope は「対象範囲の一覧」ではなく「対象と対象外が混ざった一覧」になってしまった。

MVP5 までで確認したのは「忘れない」こと。MVP6 で確認したいのは「現在状態から正しく忘れる」こと。

## 目的

Working Memory の状態変更を add / replace / remove の3つにし、「Xは対象外にする」「Xはもう不要」「Xを外す」のような明示的なユーザー発言で、現在の Working Memory から該当項目を削除できるようにする。

ただし「以前はXが対象だった」という事実まで失わないよう、変更履歴は現在状態とは別のファイルに残す。

今回やるのは「現在状態から1項目を正しく消す」ことだけで、状態管理システムには広げない。

## 成功条件

### 成功条件1: 現在状態から消える

1. scope が「商用環境を対象とする / ステージング環境を対象とする / 開発環境を対象とする」の状態で、「ステージング環境はやっぱり対象外にします」と入力する
2. CLI に `[作業記憶] scope: ステージング環境を対象とする → 削除` と表示される
3. `working_memory.json` の scope には商用環境と開発環境の2項目だけが残る。「ステージング環境は対象外とする」のような否定文は追加されない
4. 「この作業の対象環境は？」と聞くと、商用環境・開発環境と答え、ステージング環境を現在の対象として答えない

### 成功条件2: 再起動しても消えたまま

exit して再起動し、「この作業の対象環境は？」と聞いても、商用環境・開発環境と答える。

### 成功条件3: 履歴には残る

`working_memory_history.jsonl` に、ステージング環境が scope に存在したこと（add または replace のイベント）と、後から remove されたことが残っている。

### 対象外: 完了条件との不整合は自動で直さない

scope を2環境にしても、acceptance_criteria「3環境すべてに対応できていること」は書き換えない。scope の削除と完了条件の変更は別のユーザー判断である。「対象環境と完了条件は？」と聞いたとき、AI が Working Memory 上の不整合（対象は2環境なのに完了条件は3環境）を指摘できれば十分とする。

## add / replace / remove の意味

| operation | 意味 | 例 |
|---|---|---|
| add | 現在状態に新しい項目を加える | 「商用環境を対象にします」 |
| replace | 現在状態の既存項目1つを、別の内容に置き換える。置き換え後も有効な項目である | 「検証環境の代わりにステージング環境を対象にします」 |
| remove | 現在状態から既存項目1つを取り除く。代わりの項目は置かない | 「ステージング環境はやっぱり対象外にします」 |

「Xは対象外」は「対象外というXの状態」を記録するのではなく、scope からXを外すことで表す。否定文を項目として追加・置き換えしない。

## 現在状態と履歴の違い

| | Current Working Memory | History |
|---|---|---|
| ファイル | `data/working_memory.json` | `data/working_memory_history.jsonl` |
| 中身 | 今この瞬間に有効な Mission / Scope / Acceptance Criteria | Working Memory に対して行った add / replace / remove の記録 |
| 変更 | add / replace / remove で書き換わる | 追記のみ。削除しない |
| 削除した項目 | 残らない | 「以前存在した」「いつ・どの発言で消えた」が残る |
| 回答用の Claude へ | 毎回すべて渡す | 渡さない |

現在状態は履歴から再計算しない。現在状態ファイルが正であり、履歴はあとから経緯を確認するための記録である（Event Sourcing はしない）。

Long-term Memory（`memories.jsonl`）とも役割を分ける。

- Long-term Memory = 過去の経緯を含む記憶。「ステージング環境を対象にする」という古い記憶が残っていてもよい
- Working Memory = 現在有効な作業状態。Long-term Memory と矛盾する場合は Working Memory を優先する

## AI と Python の役割分担

| 担当 | やること |
|---|---|
| AI（作業記憶の抽出） | ユーザー発言が現在の作業記憶に対する追加・置き換え・削除に当たるかの意味判断。候補ごとに operation を付けて JSON で提案する。削除・置き換えの対象は、現在の作業記憶の文面をそのまま target に書く |
| AI（回答） | 現在の Working Memory を前提に回答する。Working Memory と検索で取得した長期記憶が矛盾したら Working Memory を優先する。Working Memory 内の不整合に気付いたら指摘する |
| Python | 候補の検証（field、evidence、target の実在と一意性）、状態の書き換え、現在状態の保存、履歴の追記、回答用 Claude へ現在状態だけを渡す制御 |

AI は削除候補を提案するだけで、削除はしない。AI が書いた target を手掛かりに Python が曖昧に探して消すこともしない。

## 今回やらないこと

- acceptance_criteria など他の項目の自動連動更新、項目間の dependency
- Progress 管理、Next Action、Task ID、複数タスク、作業の切り替え
- 作業完了時の自動クリア
- Working Memory 履歴の検索、履歴を回答用 Claude へ渡すこと
- relation graph、Vector DB、embedding
- Long-term Memory の superseded・削除・更新（MVP3〜MVP4 の挙動は変えない）
- 保存時の検索用 keyword
- 高度な Event Sourcing 基盤（履歴からの状態再構築、スナップショットなど）
- GUI、MCP
- Claude 呼び出し回数の最適化

## 仕様

### 抽出 AI の出力形式

入力は MVP5 と同じ（現在の Working Memory と今回のユーザー発言だけ）。出力は JSON 配列で、各要素に `operation` を付ける。

```json
[
  {"operation": "add", "field": "scope", "text": "商用環境を対象とする", "evidence": "商用環境を対象にします"},
  {"operation": "replace", "field": "scope", "target": "検証環境を対象とする", "text": "ステージング環境を対象とする", "evidence": "検証環境の代わりにステージング環境を対象にします"},
  {"operation": "remove", "field": "scope", "target": "ステージング環境を対象とする", "evidence": "ステージング環境はやっぱり対象外にします"}
]
```

| キー | add | replace | remove |
|---|---|---|---|
| operation | `add` | `replace` | `remove` |
| field | 必須 | 必須 | 必須 |
| text | 必須（新しい項目） | 必須（置き換え後） | 不要（あっても使わない） |
| target | 不要 | 必須（置き換える既存項目の文面） | 必須（削除する既存項目の文面） |
| evidence | 必須 | 必須 | 必須 |

互換: MVP5 形式（`operation` なし）も受け付ける。`replaces` があれば replace（`replaces` を target とする）、なければ add として扱う。

### Python が行う検証

全 operation 共通:

- 抽出結果全体が JSON 配列であること
- `operation` が add / replace / remove のいずれかであること
- `field` が `mission` / `scope` / `acceptance_criteria` のいずれかであること
- `evidence` が空でない文字列で、今回のユーザー入力に部分文字列としてそのまま含まれること

replace / remove:

- `target` が空でない文字列であること
- `target` がその field に現在実在する項目と一致すること
- 一致する項目がちょうど1つであること

一致の判定は MVP5 の重複判定と同じで、英字の大文字小文字・全角半角・空白の違いだけを無視した完全一致。部分一致や「似ている」項目では一致としない（例: target が「ステージング環境」なら「ステージング環境を対象とする」は削除しない）。別の field にある項目とも一致としない。

add / replace:

- `text` が空でない文字列であること
- 同じ field に同じ内容の項目が既にあれば何もしない（MVP5 と同じ）

1回の抽出結果に複数の候補があれば、前から順に、直前までの候補を反映した状態に対して検証・反映する。検証を通らなかった候補は警告を表示し、その候補だけ反映しない。

### 現在状態の保存形式

`data/working_memory.json`。形式は MVP5 から変えない。remove が成功した項目はこのファイルから本当に消える。

### 履歴ファイルの形式

`data/working_memory_history.jsonl`（UTF-8、JSONL、1行1イベント、追記のみ）。保存場所は環境変数 `ACM_WORKING_MEMORY_HISTORY_FILE` で変更できる。

```jsonl
{"timestamp": "2026-10-07T10:00:00+09:00", "operation": "add", "field": "scope", "text": "検証環境を対象とする", "evidence": "今回の作業では商用環境、検証環境、開発環境の3環境を対象にします"}
{"timestamp": "2026-10-07T10:01:00+09:00", "operation": "replace", "field": "scope", "target": "検証環境を対象とする", "text": "ステージング環境を対象とする", "evidence": "検証環境の代わりにステージング環境を対象にします"}
{"timestamp": "2026-10-07T10:02:00+09:00", "operation": "remove", "field": "scope", "text": "ステージング環境を対象とする", "evidence": "ステージング環境はやっぱり対象外にします"}
```

- `text` は add では追加した項目、replace では置き換え後の項目、remove では削除した項目（現在状態に保存されていた文面）
- `target` は replace のときだけで、置き換え前の項目
- `evidence` はその変更の根拠となったユーザー発言の抜き出し
- `timestamp` は変更を反映した時刻（ローカル時刻、ISO 8601）。会話原文や長期記憶には日時が無いが、履歴は「いつの時点でどうだったか」を残すことが目的なので付ける

保存の順序は、現在状態（`working_memory.json`）→ 履歴。現在状態の保存に失敗したら、そのターンは状態も履歴も変えない。履歴の追記だけに失敗した場合は、警告を表示し、現在状態の変更は有効なままとする。

MVP6 より前に作られた項目には、履歴の add イベントが無い。

### 通常回答時に Claude へ渡すもの

MVP5 と同じ。Working Memory は現在状態（`working_memory.json` の内容）だけを渡す。削除済みの項目と履歴は渡さない。

システム指示に次を追加する。

- Working Memory は現在有効な作業状態である
- 検索で取得した長期記憶は過去の経緯を含み、その後変更・取り消しされた内容が含まれることがある
- 両者が矛盾する場合は Working Memory を優先する
- Working Memory の項目同士が矛盾している場合（例: 対象範囲と完了条件が合わない）は、勝手に解釈を決めずに指摘する

### CLI 表示

```text
[作業記憶] scope: 商用環境を対象とする / 開発環境を対象とする      ← add（フィールドごとに1行）
[作業記憶] scope: 検証環境を対象とする → ステージング環境を対象とする  ← replace
[作業記憶] scope: ステージング環境を対象とする → 削除               ← remove
```

### Claude 呼び出し回数

MVP5 から変わらない。remove の判断は既存の作業記憶抽出の呼び出しの中で行う。

| 状況 | 1ターンあたり |
|---|---|
| 長期記憶がまだ1件も無い | 3回（通常回答・長期記憶の抽出・作業記憶の抽出） |
| 通常 | 4回（検索プラン作成・通常回答・長期記憶の抽出・作業記憶の抽出） |
| 1回目の検索が0件 | 5回（上記 + 検索語再生成） |

### エラー処理

| 状況 | 動作 |
|---|---|
| 抽出結果が不正な JSON・呼び出し失敗 | 警告を表示。そのターンは更新しない（MVP5 と同じ） |
| remove / replace の target が存在しない・一意でない・別 field にある | 警告を表示。その候補だけ反映しない |
| evidence が今回の発言に無い | 警告を表示。その候補だけ反映しない |
| `working_memory.json` の保存に失敗 | 警告を表示。状態も履歴も変えない |
| 履歴の追記に失敗 | 警告を表示。現在状態の変更は有効なまま |

いずれも会話は止めない。

## 評価方法

- 自動テスト（pytest）: Claude をモックし、保存先は `tmp_path`。remove の検証・反映、現在状態と履歴の分離、回答用プロンプトに削除済み項目と履歴が入らないこと、MVP4・MVP5 の挙動が変わらないことを確認する。
- 手動スモークテスト: 実際の `claude` で「3環境を対象」→「検証環境の代わりにステージング環境」→「ステージング環境は対象外」と入力し、「この作業の対象環境と完了条件は？」への回答、再起動後の回答、履歴ファイルの中身を確認する。
