# MVP12: 記憶の保存状態と保留中の発言を区別して回答する

状態: **実装済み・未固定**（tag 前）。基準は MVP11（コミット `6dcdd89`）

## 1. 目的と対象範囲

MVP9 以降、Current（保存済みの記憶）と関係する Pending（確認待ちの発言）があると、回答 AI は「川崎か名古屋か、どちらか一方には断定できない」という二者択一で答えがちだった（MVP9・MVP10・MVP11 のスモークテストで毎回出ていた）。

MVP12 では、**保存済みの記憶と新しい発言の優先順位を決めるのではなく、それぞれの状態を正確に説明できるようにする。**

- Current は、システムが今保持している記憶。現実の今を保証するものではない
- Pending は、実際にあったユーザーの発言。保留されているのは、記憶への反映方法（置換・共存・その他）であって、発言の真偽ではない
- 未確定の点は、発言を記憶にどう反映するか。値が違っても、二者択一として説明しない

### 今回やらないこと

Current・Pending・History のデータ構造と更新処理の変更、検索の変更、回答後の検証、Python による状態の整理（調査の案③）。

## 2. 調査で分かった原因

MVP11 のスモークテストの入力を、残っていたデータと検索語から再構成し、さらに Claude への入出力を記録して切り分けた。

- **検索は原因ではない。** 毎回、Current（川崎）と Pending（名古屋）の両方が回答 AI に渡っていた。変更履歴は渡っていない（「今の住まいは？」では検索計画が履歴を不要と判断する）
- **主な原因は回答プロンプトだった。** MVP9 で入れた「以前から記録されている値を確かな情報として先に強調し、新しい発言を補足のように扱わない」という順序の制限と、「現在値だけで断定しない」という指示が組み合わさり、回答 AI は現実の住まいを二択で論じていた。「保存済み」「確認待ち」という、記憶の状態を表す言葉も無かった
- 同じ入力で、プロンプトの該当部分だけを差し替えると二者択一は 0/3 になった。Python で整理した状態ブロックを足しても、元のプロンプトのままでは 2/3 で残った
- 副因として、Current の説明（「これは現在有効な値です」）と保留の説明（「現在値だけで断定しない」）が食い違っていた。また、取り消しの後は Current の `updated_at` と Pending の `created_at` がどちらも取り消した時刻になり、発言の前後関係が回答 AI から見えない

## 3. 変更したプロンプト（`llm.py` の `SYSTEM_PROMPT`）

### Current ブロックの説明

| 変更前 | 変更後 |
|---|---|
| ユーザーについて現在有効な長期的な情報 | このシステムがユーザーについて保存している長期的な情報（保存済みの記憶） |
| updated_at はその値になった日時 | updated_at は記憶がその値に更新された日時で、ユーザーがその発言をした日時とは限らない |
| これは現在有効な値です。現在の情報が必要なときは、この値を使ってください | 保存済みの記憶の現在の値で、その後に置き換わったことが確認されていないもの。現在の情報が必要なときは、保存済みの記憶として使う。ただし、記録の状態であって現実の今を保証しない。関係する保留があるときの伝え方は保留の説明に従う |
| （番号付きの key）すべてを現在の値として伝える | 同左。加えて、これらはどれも保存済みの値で、確認待ちの保留ではない |

### 保留についての指示

- 保留になっているのは、発言を記憶にどう反映するか（置換・共存・ほかの解釈）であって、発言があったことや発言の内容ではない
- 関係する保留があるときは、記憶の状態として3つを区別して伝える。保存済みの記憶、確認待ちの発言、まだ確定していない点
- 保存済みの記憶の値を、ユーザーの現実の今の状態として言い切らない
- 値が違っても、どちらか一方だけが正しいという二者択一として説明しない。両方が今も有効なこともある
- **3つを述べる順序は決めない。** 質問に合わせて自然で分かりやすい順にする
- 同じ属性に保留が複数あるときは、それぞれを別の発言として伝え、まとめたり1つを選んだりしない
- `target_value` が無い保留は、保留した時点で保存済みの値が無かったもの。Current にも関係する項目が無ければ、保存済みの記憶は見つかっておらず、確認待ちの発言があると伝える

指示には、評価に使った具体的な属性や値（住まい・勤務先・趣味の値）を書いていない（テストで確認している）。

### MVP9 の回帰を防ぐために残した制約

| 制約 | MVP9 で防いだこと |
|---|---|
| どの順で述べる場合も、確認待ちの発言を保存済みの記憶への補足や注記のように軽く扱わない。保存済みの記憶と同じようにはっきり伝える（**新設**。順序の制限の代わり） | 新しい発言の軽視 |
| 保留は多くの場合、現在値より後の発言。古い情報や重要度の低い情報として無視しない | 新しい発言の無視 |
| 関係する保留があるときは、現在値だけで断定しない | 古い現在値による断定 |
| 保留は事実の記録で、発言の内容が疑わしいという意味ではない。未確認なのは以前の値が今も有効かであって、新しい発言そのものではない | 発言を疑うこと |
| 保留の値を確定した現在の値として扱わない。保留があるだけで現在値を無効にしない | 保留の過大評価 |
| 保留の内容はユーザー自身の発言として伝える（「〜と伺っています」） | 同上 |
| 発言に無い生活の事情を推測して補わない、例にも挙げない | 単身赴任などの推測 |
| 応答の中で質問しても記録は更新されない。更新を約束しない | 実装していない処理の約束 |

外したのは「以前から記録されている値を確かな情報として先に強調し、新しい発言を補足のように扱うことはしない」の前半（順序の制限）だけである。後半の「補足のように扱わない」は、順序に依存しない形で残した。

#### 評価用の時刻の誤りと再実行

最初の 40 回のうち、D（勤務先）の2回と Ch の3回は、入力に `2026-10-17T10:65:00+09:00` のような日時として正しくない時刻を含んでいた。

- 原因: 評価スクリプトの時計を、テストの clock フィクスチャと同じ「分の値を文字列で連番にする」形で作り、その連番を全ケースで共有していた。テストでは連番が1テストごとに初めからになるが、評価では 60 を超えて進んだ
- 対応: 評価スクリプトの時計を、日時として1分ずつ進める形に直した。評価スクリプトはリポジトリの外（作業用の領域）にあり、リポジトリのコードとテストは変えていない
- テストへの影響: 全テストの一時データに書かれた時刻を走査し、範囲外の時刻は 0 件だった（688 passed）
- 再実行: 影響した5回（D 勤務先の修正前1・修正後1、Ch の修正前1・修正後2）だけを、正しい時刻で再実行した。入力は時刻を除いて元と完全に同じだった
- 結果: 判定は元と同じだった。D はどちらも A社・B社を2つの保存済みの値として説明し、保留扱いしなかった。Ch は3回とも、保存済み・確認待ち・未確定の点を区別し、取り消しを撤回と誤解しなかった。最初の5回も、範囲外の時刻に触れた回答は無かった。上の表は再実行の結果で数えている（件数は元の結果で数えても変わらない）。言い回しの違いは、上の注の一文だけ

最初の結果と再実行の結果は、どちらも作業用の領域に残している。

製品の経路（`python -m ai_context_memory`、検索計画も実際の Claude）でも、MVP11 スモーク R1 の取り消し後のデータのコピーで「今の住まいは？」を1回実行した。検索は現在値1件・保留1件で、回答は「保存済みの記憶では、お住まいは**川崎**です。一方で、『今は**名古屋**に住んでいます』とも伺っており、こちらは記憶への反映が確認待ちになっています。（以下、置換か両方有効かが未確定）」だった。Current と Pending は変わらなかった。

### 修正後の回答の例（C: 勤務先、取り消しの後）

```text
保存済みの記憶では、勤務先は**A社**です。

一方で、「今はB社で働いています。」とも伺っています。**B社**という発言の記憶への反映は、まだ確認待ちです。この発言は一度確認されましたが、その変更がコマンドで取り消されたため、現在は未確認の状態に戻っています。

まだ確定していないのは、B社がA社に置き換わったのか、A社とB社の両方が今も有効なのかという点です。そのため、記憶からは今の勤務先を1社に断定できません。
```
