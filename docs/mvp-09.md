# MVP9: 記憶の誤上書きを防ぎ、Pending（保留）を導入する

## 今回解決したい問題

MVP8 の構造化 Long-term Memory では、AI が subject / key / value の候補を出し、Python が機械的に状態遷移を決めていた。

- 新しい key → add
- 同じ key・同じ value → no-op
- 同じ key・違う value → **replace**

この「同じ key・違う value なら replace」が危ない。

```text
Current:  user.home_location = 川崎
入力:     単身赴任で、平日は名古屋に住んでいます。
```

この発言を3回試したところ、1回は `weekday_residence` を新しく作ったが、2回は AI が `home_location` を同じ属性と判断し、Python が「平日は名古屋」で川崎を上書きした。

**同じ属性であることと、既存の値を上書きしてよいことは、別の判断である。** MVP8 はこの2つを区別していなかった。

## 事前実験で確認したこと

実装前に、実際の Claude（Opus 5.5、effort high、Claude Code のサブスクリプション経由）で、既存値と新しい発言の関係を replace / coexist / pending / no_change に分類させる実験を 121 回行った。初期状態はすべて `user.home_location = 川崎`。

| 実験 | 回数 | 結果 |
|---|---|---|
| 手がかりのある12ケース（引っ越し・二拠点・単身赴任・実家・週末・予定・出張・詳細化・訂正・再確認・現在地・旧居の終了） | 76 | 不適切な replace 0/38、明確な更新の見逃し 0/23、decision の揺れ 0、pending 0 |
| 手がかりの乏しい6ケースと、明確な3ケース | 45 | 「名古屋に住んでいます。」など5ケースは pending 25/25。明確な3ケースは 15/15 で期待どおり |

うまくいかなかったこと:

- **「今は名古屋に住んでいます。」は 5/5 で replace** になった。「名古屋に住んでいます。」は 5/5 で pending だったので、「今は」の2文字で判断が変わる。発言は川崎の終了に触れていない
- そのとき AI は `old_value_status = ended`（既存値は終わったと明示されている）と**自己申告した**。漏れた推論文には「"今は" which implies change … I'd say "ended"」とあり、含意にすぎないと分かったうえで「明示」に分類していた
- 5回とも同じ判断で、揺れではない。試行回数を増やしても、多数決を取っても見つからない種類の失敗である
- 121 回中 7 回、JSON の前に `<reasoning>` などの推論文が漏れ、通常の JSON 解析に失敗した

ここから分かったこと:

1. 明確な更新・共存・一時滞在は、AI に任せて安定して判断できる
2. AI は「まだ分からない」と判断できる（pending を選べる）
3. しかし **AI の判断を、同じ出力の別フィールドで AI 自身に検証させても、独立した安全確認にはならない**。誤った replace と、それを正当化する申告は同時に出てくる

これが MVP9 の出発点である。事前実験でうまくいったケースも、AI の判断が常に正しいことを示すものではない。

## 目的

1. AI が新旧の記憶の関係を判断する
2. Python が危険な上書きを制限する
3. 関係を確定できない場合は、新しい発言を Pending として保存する

**新しい情報を保存することと、既存の現在値を無効にすることを分ける。**

Pending は「新しい発言が嘘・不確か」という意味ではない。

```text
Current:   user.home_location = 川崎
新しい発言: 今は名古屋に住んでいます。
```

- 「名古屋に住んでいる」という発言は確実に存在する
- 川崎の住まいが終わったかは分からない
- 川崎は消さない
- 名古屋の情報も捨てない

## 成功条件

### Python が保証すること（AI が何を返しても成り立つ）

| # | 条件 |
|---|---|
| P1 | 既存 key の値が変わるのは、AI が replace と判断し、かつ下記「replace の実行条件」をすべて満たしたときだけ |
| P2 | coexist は、Current に無い key への追加だけを行う。既存 key と衝突したら上書きしない（同じ値なら何もしない、違う値なら Pending） |
| P3 | pending と no_change は Current を変更しない |
| P4 | replace の実行条件を満たさない場合は、捨てずに Pending へ格下げする。新しい発言の値・evidence・確認質問が残る |
| P5 | 不正な出力（JSON でない、不明な decision、subject が user でない、evidence が発言に無い）は反映しない。会話は止めない |
| P6 | Pending は Current とは別ファイルに保存され、再起動後も読み込まれる。完全一致相当の重複は保存しない |
| P7 | Current / History の形式は MVP8 と同じ。既存ファイルの migration はしない。Pending ファイルが無くても起動できる |

### 実際の Claude で確認すること（スモークテスト）

初期状態はすべて `user.home_location = 川崎`。各ケースの前に初期状態へ戻す。

| # | 入力 | 期待 |
|---|---|---|
| A | 名古屋に住んでいます。 | Current の川崎は残る。名古屋は Pending に保存される |
| B | 今は名古屋に住んでいます。 | Current の川崎は無条件には消えない（AI が replace と言っても Python が格下げする）。名古屋は Pending に保存される |
| C | 川崎の家を引き払って、名古屋に引っ越しました。 | 明示的な変更として replace できる。History に replace が残る |
| D | 平日は名古屋、週末は川崎で暮らしています。 | coexist。川崎は残り、平日の住まいが別の key で追加される。History に add が残る |
| E | 今日は出張で名古屋に来ています。 | no_change。何も変わらない |
| F | Pending がある状態で再起動し「今の住まいは？」 | 検索で Current と関連する Pending の両方が渡り、古い Current だけで断定せず、名古屋という発言と、川崎が今も有効かは未確認であることを分けて答える |
| G | 1+1は？ | Pending の検索をしない |

スモークテストは期待どおりにならなくても、結果をそのまま記録する。結果を見てプロンプトを調整し、成功した結果だけを残すことはしない。

### 自動テスト

- 既存のテストを維持する。ただし MVP8 の「同じ key・違う value なら replace」を前提にしたテストは、MVP9 で意図的に変える挙動なので、MVP9 の仕様に合わせて書き換える（どれを変えたかは報告する）
- 状態遷移・上書き保護・永続化・回答・JSON の各観点のテストを追加する。pytest では実際の Claude を呼ばない

## AI と Python の役割

| 担当 | やること |
|---|---|
| AI（関係判断） | 発言のどこがユーザー自身の長く有効な属性か、それが既存のどの key と関係するか、既存値と新しい発言の関係（replace / coexist / pending / no_change）、旧値の終了・訂正を述べた部分の抜き出し、確認質問 |
| Python | 出力の解析と検証、replace の実行条件の確認、Pending への格下げ、Current・History・Pending の保存、重複の抑制、検索、件数の上限 |
| AI（検索プランナー） | 長期記憶が必要かと検索語（MVP8 から変更なし。同じ検索語で Pending も検索する） |
| AI（通常回答） | Current・Pending・History・従来の記憶を、優先関係に従って使い分けて答える |

「AI が頭脳、Python が手足」は変えない。ただし手足は、AI が replace と言っただけでは上書きしない。

## replace / coexist / pending / no_change

| decision | 意味 | Python の動作 |
|---|---|---|
| replace | 既存の値が、もう現在の値ではない（終わった・変わった・誤りだった）と発言が明確に示している | 実行条件をすべて満たせば Current を置き換え、History に replace を残す。満たさなければ Pending へ格下げ |
| coexist | 既存の値を変えずに、新しい属性として追加できる（既存と両立する情報、または既存のどれとも関係しない新しい属性） | proposed_key が Current に無ければ add。あれば上書きしない（同じ値なら何もしない、違う値なら Pending） |
| pending | 記憶する価値はあるが、既存の値が今も有効なのか置き換わったのかを発言だけでは判断できない | Current は変えず、Pending に保存する |
| no_change | 状態を変える必要がない（一時的な状況、既存値の再確認、過去の値だけの話など） | 何もしない |

MVP8 にあった「新しい key → add」は、coexist（既存の key に関係しない新しい属性）に含める。

no_change は「記憶する価値がない」という意味ではない。今回は no_change の情報を長期状態には保存しないが、元の発言は `conversation.jsonl` に残り、従来の長期記憶（`memories.jsonl`）の抽出も MVP8 までと同じく行われる。

### 更新と訂正

「引っ越した」（世界が変わった）と「さっきの川崎は間違いだった」（発言の訂正）は、AI が `old_value_status` で `ended` / `wrong` と区別して返す。ただし MVP9 では状態遷移としては区別せず、どちらも replace として扱う。History の形式も変えない。

## AI の出力形式

MVP8 の構造化抽出の Claude 呼び出しを、関係判断つきの出力に置き換える。呼び出しを1回増やすのではなく、同じ1回の中で判断させる。入力は MVP8 と同じで、Current の全項目（subject / key / value）と今回のユーザー発言だけ。

1つの発言に複数の属性が含まれることがあるので（MVP8 から）、出力は事前実験の1オブジェクトではなく JSON 配列にする。各要素が属性1つについての判断である。扱う属性が無ければ `[]`。

```json
[
  {
    "decision": "pending",
    "subject": "user",
    "target_key": "home_location",
    "proposed_key": null,
    "proposed_value": "名古屋",
    "evidence": "今は名古屋に住んでいます。",
    "old_value_status": "not_stated",
    "old_value_evidence": null,
    "temporal_scope": "current",
    "reason": "川崎の住まいが終了したかは発言に示されていない。",
    "confirmation_question": "川崎には今も住んでいますか？"
  }
]
```

| キー | 内容 |
|---|---|
| `decision` | replace / coexist / pending / no_change |
| `subject` | 常に `user` |
| `target_key` | 関係する既存の key（Current にある key をそのまま）。無ければ null |
| `proposed_key` | coexist で追加する新しい key（snake_case） |
| `proposed_value` | 記憶する値。replace では新しい値。発言から値が分からなければ null |
| `evidence` | 根拠の部分を発言から一字一句そのまま抜き出したもの |
| `old_value_status` | 発言が既存値について述べていること（ended / wrong / continues / not_stated） |
| `old_value_evidence` | replace のときだけ。既存値が終わった・変わった・誤りだったことを述べた部分を、発言から一字一句そのまま抜き出したもの |
| `temporal_scope` | current / temporary / future / past / none |
| `reason` | 判断理由 |
| `confirmation_question` | pending のとき、確認の質問を1つ。replace のときも、自動で確定できない場合に備えて1つ |

事前実験の分類プロンプトをベースにし、MVP8 の抽出指示（扱う情報・扱わない情報、key の再利用、key と value の形式、evidence の抜き出し）を統合する。変更点は次の4つ。

- 出力を JSON 配列にした
- `old_value_evidence` を追加した
- `memory_worthy` を外した（Python が使わないため）
- replace のときも確認質問を出させるようにした

この統合は事前実験とは別のプロンプトになるので、事前実験の結果がそのまま再現される保証はない。スモークテストで確認する。

## replace の実行条件（Python）

最も重要な部分である。**AI が replace と言っただけでは、Python は Current を上書きしない。** 次をすべて満たすときだけ置き換える。

| # | 条件 | 誰の情報か |
|---|---|---|
| R1 | `target_key` が Current に存在する | Python が確認する事実 |
| R2 | `proposed_value` が空でない（Current と同じ値なら no-op） | Python が確認する事実 |
| R2b | `proposed_value` が今回の発言にそのまま現れる（MVP9 仕上げで追加） | Python が確認する事実 |
| R3 | `evidence` が今回の発言に一字一句含まれる | Python が確認する事実 |
| R4 | `old_value_status` が `ended` または `wrong` | AI の自己申告 |
| R5 | `temporal_scope` が `current` | AI の自己申告 |
| R6 | `old_value_evidence` が今回の発言に一字一句含まれる | Python が確認する事実 |
| R7 | `old_value_evidence` の中に、Current の既存の値がそのまま現れる | Python が確認する事実 |
| R8 | `old_value_evidence` の中に、終了・変更・訂正を表す表現（下記の短い一覧）のどれかが現れる | Python が確認する事実 |

どれか1つでも満たさなければ、Current は変えずに Pending へ格下げする。格下げした理由（どの条件を満たさなかったか）を Pending に残し、CLI にも表示する。

R4・R5 は AI の自己申告で、事前実験で示したとおり安全確認にはならない。**自己申告は replace を止める方向にだけ使い、replace を許可する根拠にはしない。** 許可の根拠は、発言の原文に対して Python が確認できる R1〜R3・R2b・R6〜R8 である。

R2b は、新しい値もユーザー自身が述べたものに限るための条件で、evidence の原文一致と同じ種類の確認である。AI が発言に無い値を作って replace を返した場合（例: 「川崎の家は引き払っていません。」に対して、新しい値「名古屋」を作る）を止める。表記の違い（発言「名古屋」に対して値「名古屋市」）も止めるが、その場合は Pending になるだけである。

R8 の表現は、既存値の終了・変更・訂正を述べるときに現れる、属性の種類によらない短い語幹だけにする（15個）。

```text
引き払 / 引っ越 / 転居 / 退去 / 離れ / 辞め / やめ / 退職 / 転職 / 終わ / 変わ / 変え / 間違 / 誤り / 訂正
```

これは意味の判定ではない。「この語が無ければ自動では置き換えない」という必要条件で、語が足りなくて置き換えられないものは Pending になるだけである。一覧を増やして意味を判定する方向には進めない。

### この制約で防げるもの

| 発言（Current: 川崎） | AI が誤って replace + ended と返した場合 | 止める条件 |
|---|---|---|
| 今は名古屋に住んでいます。 | 格下げ | R6 または R7（川崎に触れていない） |
| 名古屋に住んでいます。／家は名古屋です。 | 格下げ | R7 |
| 川崎にも住んでいますが、名古屋にも家があります。 | 格下げ | R8（川崎は現れるが、終了・訂正の表現が無い） |
| 単身赴任で、平日は名古屋に住んでいます。（MVP8 の誤置換） | 格下げ | R7 |
| 引っ越しました。（新しい値が無い） | 格下げ | R2 |
| 川崎の家は引き払っていません。（否定。新しい値が発言に無い） | 格下げ | R2（値なし）または R2b（AI が作った値） |
| 川崎の職場を辞めました。（住まいではない。新しい値が発言に無い） | 格下げ | R2 または R2b |
| 来月、川崎から福岡に引っ越す予定です。 | 格下げ | R5（AI が temporal_scope を future と返した場合だけ） |

### この制約で防げないもの

**この制約は完全な意味の検証ではない。** Python が確かめているのは「新しい値と旧値が発言に現れ、旧値の近くに終了・変更・訂正の語がある」という文字列の事実だけで、その語が旧値の終了を肯定しているのか、何が終わったのかは分からない。次のような場合、AI が誤って replace と判断すると、すべての条件を満たしてしまう。

- 否定で、新しい値も発言にある: 「川崎の家は引き払っていません。名古屋にも部屋を借りました。」（「川崎」「引き払」「名古屋」がすべて現れる）
- 別のものの終了で、新しい値も発言にある: 「川崎の職場を辞めて、名古屋の会社に移りました。」（住まいではない）
- 予定: 「川崎から福岡に引っ越す予定です」で、AI が temporal_scope も current と誤った場合
- 抜き出しが広すぎる: AI が発言全体を `old_value_evidence` にすると、川崎と終了の表現が別々の文にあっても通る

上の2つの例は、pytest に `xfail(strict=True)`（既知の限界として失敗することを確かめるテスト）として残してある。否定の語（「ません」「ない」）や属性ごとの名詞（「家」「職場」）を Python の一覧に足せば一部は止められるが、それは Python に意味を判定させることになり、一覧の外の言い方は止められないまま、正しい更新を誤って止める場合も増える。MVP9 では足さず、この範囲は AI の判断に頼っていることを限界として明記する。

逆に、正しい更新でも自動では置き換えられず Pending になるもの:

- 旧値に触れない更新:「横浜に引っ越しました。」「さっきのは間違いで、本当は横浜です。」
- 表記の違い: Current が「川崎市」で発言が「川崎の家を引き払って」（R7 は Current の値がそのまま現れることを求める）
- 一覧に無い言い方:「最近は好きな果物はりんごです。」「梨よりりんごが好きになりました。」

**MVP8 の成功条件2（梨 → りんごで replace）は、MVP9 では Pending になる。** 「最近は」は梨の終了を明示していないからで、意図した変更である。

## coexist の実行条件（Python）

- `proposed_key` が snake_case・64文字以内（MVP8 と同じ形式）
- `proposed_value` が空でない
- `evidence` が発言に一字一句含まれる
- `proposed_key` が Current に無ければ add し、History に add を残す
- `proposed_key` が Current にあれば上書きしない。同じ値なら何もしない。違う値なら Pending にする（理由: key の衝突）

1つの発言の中で同じ key（replace の target_key、coexist の proposed_key）を2回変えようとした場合は、最初の1つだけを使う（MVP8 と同じ）。

## Pending の保存形式

`data/long_term_memory_pending.json`（環境変数 `ACM_LONG_TERM_MEMORY_PENDING_FILE` で変更可）

```json
{
  "items": [
    {
      "id": "p001",
      "subject": "user",
      "target_key": "home_location",
      "target_value": "川崎",
      "proposed_key": null,
      "proposed_value": "名古屋",
      "evidence": "今は名古屋に住んでいます。",
      "decision": "replace",
      "hold_reason": "old_value_evidence がありません",
      "reason": "「今は」と現在の居住地を明示しており、川崎はもう現在の値ではない。",
      "confirmation_question": "川崎には今も住んでいますか？",
      "status": "unresolved",
      "created_at": "2026-10-14T10:00:00+09:00"
    }
  ]
}
```

| キー | 内容 |
|---|---|
| `id` | `p001` からの連番 |
| `target_key` / `target_value` | 関係する既存の key と、保留した時点のその値（無ければ null） |
| `proposed_key` / `proposed_value` | 発言が述べた属性と値（分からなければ null） |
| `evidence` | 発言からの抜き出し（Python が原文との一致を確認済み） |
| `decision` | AI の元の判断（pending、または格下げ前の replace / coexist） |
| `hold_reason` | Python が格下げした理由。AI 自身が pending を選んだときは null |
| `reason` / `confirmation_question` | AI の判断理由と確認質問。格下げした replace に質問が無ければ、Python が既存値を確かめる汎用の質問を入れる |
| `status` | 常に `unresolved`（解決処理は次の MVP） |
| `created_at` | Current の `updated_at` と同じ形式 |

- Pending を保存しても Current も History も変えない。History は Current の変更記録のままにする
- 重複の判定は subject・target_key・proposed_key・proposed_value・evidence が同じかどうか（英字の大文字小文字・全角半角・空白の違いだけを無視する）。AI の reason や質問の言い回しの違いは見ない
- 保存の順序は Current → History → Pending。Pending の保存に失敗しても警告だけで、Current の変更は有効なまま
- ファイルが壊れていたら、起動時にエラーを表示して中止する（Current と同じ）

## 回答時の Current と Pending

Pending を保存するだけでは、回答 AI は古い Current だけを見て「川崎です」と断定してしまう。回答時にも関連する Pending を渡す。

### 取得（Python）

毎回全件は渡さない。Claude 呼び出しは増やさない。

1. 検索プランナーが長期記憶を必要と判断したときだけ、同じ検索語（`queries`）で Pending も検索する（検索対象: subject / target_key / target_value / proposed_key / proposed_value / evidence）
2. Current の検索でヒットした項目の key と、`target_key` または `proposed_key` が同じ Pending も取得する（例: `home_location` がヒットしたら、`home_location` についての Pending）
3. 最大5件。key でつながったものを優先し（多すぎる場合は新しく保存されたものを残す）、保存順に並べる
4. 従来の記憶・Current が0件でも Pending がヒットすれば、再検索しない

### 回答 AI への指示

回答用のプロンプトに `[long-term memory pending]` ブロックを足す（Current の直後、History の前）。

- Current は確定済みの現在の値
- Pending は、ユーザーがそう述べたという事実の記録で、既存値との関係がまだ確認できていないもの。発言が疑わしいという意味ではない
- Pending は多くの場合 Current より後の発言である。古い情報・優先度の低い情報として無視しない
- 関係する Pending があるときは、Current の値だけで断定しない
- Pending の値を、確定した現在の値として扱わない
- Pending があるというだけで、Current を無効になったものとして扱わない
- 関係する Pending があるときは、ユーザーが新しく述べたこと（Pending の evidence）、以前から記録されている値（Current）、両者の関係が未確認であること、の3つを区別して伝える（MVP9 仕上げ）
- Pending の内容はユーザー自身の発言として伝える（例: 「〜と伺っています」）。未確認なのは以前の値が今も有効かどうかで、新しい発言そのものではない。以前の値を確かな情報として先に強調し、新しい発言を補足のように扱わない（MVP9 仕上げ）。ただし Pending を常に Current より優先するわけではない
- 関係を説明するために、発言に無い生活の事情（理由、家族、仕事、住まい方など）を推測して補わない。例として挙げることもしない（MVP9 仕上げ）
- Pending を確認して記録を確定・更新する機能はまだ無いので、「答えれば記録を更新する」といった約束をしない。未確定な関係を説明するところまでにし、確認の質問はしなくてよい（MVP9 仕上げ）
- 従来の記憶に Pending と同じ内容があっても、それだけで確定したものとして扱わない

### 優先関係

1. 現在の会話でのユーザー発言（これまでと同じ）
2. 確定済みの現在の値（Current）と、未確認の新しい発言（Pending）。Pending は Current を上書きも無効化もしない。両方を述べる
3. 変更履歴（History）は過去の値の根拠。現在の値としては使わない
4. 従来の記憶（`memories.jsonl`）は Current と矛盾すれば Current を優先する

## CLI 表示

```text
[長期状態] user.home_location: 川崎 → 名古屋        ← replace
[長期状態] user.weekday_residence: 名古屋            ← coexist（add）
[長期保留] user.home_location: 名古屋（現在の値「川崎」は変更していません）
[長期保留の理由] AIの判断は replace でしたが、自動では置き換えませんでした: …   ← 格下げのときだけ
[長期保留の確認事項] 川崎には今も住んでいますか？（表示のみです。回答しても保留は自動では確定しません）
[長期保留検索] home_location / 住まい
[長期保留検索結果] 1件
```

確認質問は表示するだけで、MVP9 ではユーザーの回答を解釈して Pending を確定する処理はしない。

## JSON 形式の崩れへの対応

事前実験の 121 回中 7 回、JSON の前に推論文が出た（いずれも推論文のあとに正しい JSON が続き、JSON のあとには何も無かった）。

MVP9 では、**再試行（A）ではなく、出力から JSON を安全に取り出す方法（B）** を採る。再試行は Claude 呼び出しが増え、再試行でも同じことが起こりうる。取り出す方法は決定的で、テストで挙動を固定できる。

1. まず通常どおり解析する（コードブロックの囲みは MVP8 と同じく外す）
2. 失敗したら、出力の中から JSON の値（`{` か `[` で始まり、それ自体で完結するもの）を左から探す
3. 見つかった JSON の値が**ちょうど1つ**で、それが**出力の末尾**にある（後ろに空白しか無い）ときだけ使う
4. 0個、2個以上、末尾でない場合は失敗にする。どれかを選んだり、途中を切り貼りして直したりしない
5. 取り出した JSON にも、通常と同じ検証（JSON 配列であること、decision、subject、evidence の原文一致、replace の実行条件）をすべて行う
6. 取り出した場合は、CLI に警告を1行表示する（取り出した回数を数えられるように）
7. 失敗したら、そのターンは Current も Pending も変えない

対象は構造化 Long-term Memory の抽出だけで、検索プランや作業記憶の抽出は MVP8 と同じ。

限界:

- 推論文の中に JSON らしい断片（例えば `[]`）があると、候補が2つになって失敗する（安全側）
- JSON のあとに説明文が付いた出力は救えない（安全側）
- 取り出した回数は CLI の表示だけで、ファイルには残らない

## Claude 呼び出し回数

構造化抽出の呼び出しを置き換えるだけなので、MVP8 と同じ。

| 状況 | 1ターンあたり |
|---|---|
| 検索できるものが何も無い | 4回（通常回答・長期記憶の抽出・構造化抽出・作業記憶の抽出） |
| 通常 | 5回（検索プラン作成 + 上記4回） |
| 長期記憶の1回目の検索が0件 | 6回 |

Pending の検索は Python の文字列検索で、Claude を呼ばない。

## エラー処理

| 状況 | 動作 |
|---|---|
| 抽出結果が不正な JSON・呼び出し失敗 | 警告を表示。Current も Pending も変えない |
| 要素が検証を通らない（不明な decision、subject、evidence、key の形式） | 警告を表示。その要素だけ反映しない |
| replace の実行条件を満たさない | Pending へ格下げし、理由を表示 |
| Current の保存に失敗 | 警告を表示。Current も History も変えない（Pending の保存は試みる） |
| History の追記に失敗 | 警告を表示。Current の変更は有効なまま |
| Pending の保存に失敗 | 警告を表示。Current の変更は有効なまま |
| Pending ファイルが無い | 0件として起動する |
| Pending ファイルが壊れている | 起動時にエラーを表示して中止する |

いずれも会話は止めない。

## 今回やらないこと

- Pending の確認質問をユーザーへ自動で出すこと、回答の解釈、Pending の確定・削除・期限切れ
- 1つの key に複数の値を持たせること
- 更新と訂正の状態遷移・History 形式での区別
- Current / History の保存形式の変更、既存データの migration
- 予定（未来の値）の期限管理
- key の階層化、ontology、relation graph、ベクトル検索
- 検索プランや作業記憶の抽出への JSON 取り出しの適用
- Claude 呼び出し回数の最適化
- GUI、MCP

## 残る安全上の限界

- replace の実行条件は完全な意味の検証ではなく、AI の判断がおおむね正しいことを前提にした**二重の網**である。AI が replace を誤り、かつ新しい値が発言にあり、抜き出しが R6〜R8 を満たす場合（否定、別のものの終了、広すぎる抜き出し）は上書きされる。Python は意味を検証していない
- coexist は既存値を消さないが、既存値が今も有効であることを確認したわけではない（例: 単身赴任で coexist になっても、川崎の家が残っているかは発言に無い）
- no_change と判断された情報は長期状態に残らない。AI が誤って no_change にした新しい情報は、従来の長期記憶と会話原文にしか残らない
- Pending は解決されないので、溜まっていく。回答時に渡すのは関連するものの上位5件だけ
- 回答 AI が Pending と Current を正しく使い分けるかはプロンプトの指示に頼っている
- 事前実験・スモークテストは住まいの話題だけで、長期状態の項目も1つだけだった

## MVP9 仕上げでの検証結果

MVP9 を固定する前に、スモークテストで見つかった問題を限定的に直し、追加で検証した。

### replace の条件の回帰テスト

AI が誤って replace（old_value_status = ended）を返した場合を想定した。

| 発言 | AI の誤った出力 | 修正前 | 修正後（R2b 追加） |
|---|---|---|---|
| A. 川崎の家は引き払っていません。 | 新しい値なし | 保留（R2） | 保留（R2） |
| A. 同上 | 発言に無い値「名古屋」を作る | **上書きされた** | 保留（R2b） |
| B. 川崎の職場を辞めました。 | 新しい値なし | 保留（R2） | 保留（R2） |
| B. 同上 | 発言に無い値「名古屋」を作る | **上書きされた** | 保留（R2b） |
| C. 川崎にも住んでいますが、名古屋にも家があります。 | 抜き出しが狭い／発言全体 | 保留（R8） | 保留（R8） |
| D. 川崎の家を引き払って、名古屋に引っ越しました。 | 正しい replace | replace | replace |
| A'. 川崎の家は引き払っていません。名古屋にも部屋を借りました。 | 新しい値「名古屋」 | 上書きされた | **上書きされる（既知の限界）** |
| B'. 川崎の職場を辞めて、名古屋の会社に移りました。 | 新しい値「名古屋」 | 上書きされた | **上書きされる（既知の限界）** |

### 単身赴任（実際の Claude、初期状態から独立に3回）

「単身赴任で、平日は名古屋に住んでいます。」は、3回とも AI が coexist（`weekday_residence: 名古屋`、old_value_status = not_stated）を返し、Python が add した。3回とも川崎は Current に残り、History には add だけが残った（replace は無かった）。Pending は作られなかった。

### Pending を含む回答（実際の Claude、独立に3回）

Current `home_location = 川崎` と Pending「今は名古屋に住んでいます。」を用意して再起動し、「今の住まいは？」と聞いた。3回とも、名古屋の発言を先に「伺っています」と伝え、川崎を以前の記録として示し、関係が未確認だと説明した。単身赴任などの推測、記録の更新の約束、確認の質問は3回とも無かった。

ただし3回とも「どちらが今のお住まいかは断定できません」と結んでおり、未確認なのは「川崎が今も残っているか」なのに、「名古屋か川崎か」の二者択一として説明していた。問題は小さくなったが、残っている。プロンプトは再調整していない。
