# MVP13: 属性単位で記憶の変更経緯を取得する

状態: **実装済み・未固定**（tag 前）。基準は MVP12（コミット `b3a832d`、タグ `article-14`）

## 1. 目的と対象範囲

MVP12 までは、長期状態の現在値（Current）・保留（Pending）・変更履歴（History）を、検索プランの検索語でそれぞれ別々に検索し、ヒットしたものだけを回答AIへ渡していた。そのため「なぜ住まいの記憶が変わったの？」で、検索語が `replace` / `revert` だと replace と revert のイベントだけが渡り、最初に川崎を記憶した add が欠けることがあった。

MVP13 では、検索語を足すのではなく、**検索は関係する属性を見つけるためだけに使い、見つかった属性の現在値・未解決の保留・変更履歴を Python が決定的に集める**ようにした（AI が関連性を見つけ、Python が関連する記憶を漏れなく集める）。

### 今回やらないこと

データ形式の変更、記憶の追加・確認・取り消しの処理の変更、検索プランナーの指示の変更、プランナーへ属性一覧を渡すこと（調査の案③）、発言・確認・取り消しを1本にした時系列ブロック（案④）。

## 2. 調査で分かった原因（要約）

調査では、一時データ（川崎を add → 名古屋を保留 p001 → `/confirm` で置換 → `/revert` で取り消し、p002 に戻る）に対して、実際の Claude の検索プランナーを 6問×2回 実行した。

| 質問 | 取得できなかったもの |
|---|---|
| なぜ住まいの記憶が変わった？／以前は？／いつ変更？（6回） | 6回とも revert（プランナーは key を `residence` / `address` と推測し、外れた。revert には evidence が無いので、発言の言葉でも当たらない） |
| 記憶が変わった経緯を教えて（2回） | 2回とも Current と Pending（`needs_memory=false` で、変更履歴だけを検索した） |
| 名古屋の件はどうなった？（2回） | 2回とも Current（保留の名古屋から、現在値の川崎へつながらない） |

原因は、イベント単位の文字列一致で検索していたこと、Current・Pending・History を互いに結び付ける処理が無かったこと（現在値 → 保留の一方向だけ）、変更履歴の上限（10件）で同点なら古いイベントから落ちること、だった。

## 3. 属性単位の展開の仕組み

### 属性の特定

1. 検索プラン（AI）と各検索（Python）は MVP12 までと同じに実行する
2. ヒットした項目から、属性 `(subject, attribute_base(key))` を取り出す。並びは次の順で、それぞれのヒットの順位順
   - 現在値でヒットした項目（スコア順）
   - 検索語でヒットした保留の `target_key` と `proposed_key`（スコア順）
   - 変更履歴でヒットしたイベント（スコアの高い順、同点は新しい順。`rank_memory_history`）
3. 番号付きの key は、既存の規則（`_` と2以上の番号で終わる key は番号の無い key と同じ属性。`home_location_2` → `home_location`）でまとめる。subject が違えば別の属性

### 集める

| | 対象の属性 | 集めるもの | 上限 |
|---|---|---|---|
| Current | 先頭から最大5つ（`MAX_ATTRIBUTES`）。ただし、変更履歴だけでヒットした属性は、変更履歴を渡すものに限る | その属性の全項目（番号付きの key を含む） | 属性の数だけ |
| Pending | 同上 | 未解決の保留のうち、`target_key` か `proposed_key` がその属性のもの、と検索語でヒットした保留 | 合わせて5件（MVP9 と同じ） |
| History | 変更履歴の検索が必要と AI が判断したターンだけ。先頭から5つのうち、変更履歴のある属性を先頭から最大3つ（`MAX_HISTORY_ATTRIBUTES`） | その属性のイベントを、検索語によらず全件から古い順 | 1つの属性で10件（`MAX_ATTRIBUTE_HISTORY_EVENTS`）。超えたら古いほうを省く |

- 変更履歴でヒットした属性は、`needs_memory` が false でも Current と Pending を渡す
- 保留だけでヒットした属性（名古屋）も、その属性の Current（川崎）を渡す
- 変更履歴の検索語が1件も当たらなくても、現在値・保留でヒットした属性の変更履歴を渡す（key の推測違いを、値や発言の言葉で見つけた属性で補う）
- 変更履歴の検索が不要と判断されたターン（「今の住まいは？」など）では、変更履歴は渡さない（MVP12 の入力と同じ）
- 確認・取り消しの識別子と根拠（`pending_id`、`confirmation_id`、確認の質問・回答・承認、`revert_id`、`reopened_pending_id`、取り消しの承認）は、MVP11 までと同じくイベントに付けて渡す

### 「変更履歴だけでヒットし、変更履歴を渡さない属性」を Current に含めない理由

最初の実装では、変更履歴だけでヒットした属性も先頭5つまで Current を渡していた。実際の Claude の評価（後述の13属性のケース）で、属性を特定しない検索語（`add` / `replace` / `revert`）のとき、変更履歴を渡さない属性（3つの上限から外れた `attr_j`・`attr_k`）の現在値が2つ渡り、回答AIが「保存済みの値は見つかりましたが、変更履歴は今回取得できていません」と説明し、省いた属性の数とも二重に数えた。属性を特定しない検索語で無関係な属性の現在値を増やさないよう、変更履歴だけでヒットした属性は、変更履歴を渡す属性に限って Current と Pending を渡すように直した。

## 4. 履歴の完全性の表し方

変更履歴のブロックは、属性ごとに見出しの行を付けてまとめる。

```text
[long-term memory history]
attribute: user.home_location (events: 3 of 3, complete)

- 2026-10-17T10:01:00+09:00
  operation: add
  ...

attribute: user.employer (events: 10 of 14, 4 older events omitted)

- ...

other matching attributes not included: 11
[/long-term memory history]
```

| 表示 | 意味 |
|---|---|
| `events: N of N, complete` | その属性の変更履歴を、記録されている全件渡した |
| `events: 10 of 14, 4 older events omitted` | 新しい10件だけ渡し、古い4件を省いた |
| `other matching attributes not included: N` | 検索で見つかったが、変更履歴を渡していない属性の数 |
| 見出しの無い属性 | 変更履歴を渡していない（検索が不要と判断された、または変更履歴に1件も無い） |

状態ごとの扱い:

| 状態 | 回答AIへ渡るもの | CLI | 確認したテスト |
|---|---|---|---|
| 属性が見つかった・履歴を全件渡した | 見出し `events: N of N, complete` とイベント | `[長期履歴] user.key N/N件` | `test_replace_and_revert_hits_bring_the_whole_history_of_the_attribute` ほか |
| 属性が見つかった・履歴の一部を省いた | 見出し `events: 10 of 14, 4 older events omitted`、または `other matching attributes not included: N` | `10/14件`、`ほかに N 属性の変更履歴は渡していません` | `test_long_history_of_one_attribute_keeps_the_newest_events_and_says_so`、`test_too_many_attributes_are_capped_and_the_omission_is_stated` |
| 属性が見つからなかった | 何も渡さない（ブロックごと無い） | `[長期履歴検索結果] 0件` のみ | `test_attribute_that_cannot_be_found_sends_nothing_and_claims_nothing` |
| 属性は見つかったが、その属性の履歴が0件 | 見出しを付けない（「履歴が無い」とは書かない） | 表示なし | `test_attribute_without_recorded_events_is_not_described_as_having_none` |
| 履歴ファイルの読み込みに失敗 | 変更履歴を渡さない（見出しも付けない）。Current と Pending は渡す | `[警告] 長期状態の変更履歴が…` | `test_unreadable_history_is_not_treated_as_empty`、`test_broken_history_file_is_a_warning_and_conversation_continues` |

- 「属性を特定できたこと」と「その属性の履歴がすべてそろっていること」を別々に示す。前者は見出しの行があること、後者は `complete` かどうか
- 変更履歴に1件も無い属性には見出しを付けない（「履歴が無い」とは書かない）。変更履歴のファイルが読めなかったターンも、変更履歴は渡さない（読めないことを「記録が無い」と扱わない）
- 読み込みの失敗は、Python（`memory_events_loaded`）と CLI の警告では区別しているが、回答AIには「失敗した」とは伝えていない。回答AIから見ると「履歴が見つからなかった」と同じで、「見つからなかったことは存在しないことを意味しない」の指示で扱う（残る問題）
- CLI には、検索の表示の後に `[長期履歴] user.home_location 3/3件` のように、渡した件数と全件数を表示する。`[長期履歴検索結果]` は MVP12 までと同じく、検索語にヒットしたイベントの数

## 5. 回答AIへの指示（追加したものだけ）

MVP12 までの指示は変えていない。`[long-term memory history]` の説明に次を足した。

| 追加した指示 | 目的 |
|---|---|
| 属性ごとにまとめて古い順に並べていること、見出しの行の意味（`complete` / `older events omitted` / `other matching attributes not included`） | 一部の履歴だけで全経緯のように説明させない |
| 見出しのある属性の保存済みの値は `[long-term memory state]` にすべて含めている。無ければ、その属性に今保存されている値は無い | 共存の取り消しで外した key などを、履歴から現在値と推定させない |
| 今の保存状態は Current と Pending のブロックだけを根拠にし、変更履歴の最後のイベントの value や `reopened_pending_id` から推定して言い切らない | History だけから現在の保存状態を断定させない |
| 保留を確認して行った変更の日時は確認した日時で、元の発言の日時とは限らない | 「いつ変更した？」で、確認の日時を発言の日時と取り違えさせない |
| 発言・確認の質問と回答・実行の承認・取り消しを別の出来事として区別する。変更の理由として述べてよいのは記録にあることだけで、記録に無い理由や生活の事情を推測しない | 変更の発生・承認・取り消しの区別と、理由の推測の防止 |
| 検索で見つからなかったことは、記憶や変更履歴が存在しないことを意味しない。記録が無いと断定せず、見つけられなかったと伝える | 属性を見つけられなかった場合の誤認の防止 |

指示には評価に使った値（川崎・名古屋・A社・B社）を書いていない（テストで確認）。システムプロンプトは 6,349 文字から 7,286 文字になった。

#### 履歴が渡らなかった1問（「名古屋の件はどうなった？」）

- 検索プラン: `needs_memory: true`、`queries: ["名古屋", "なごや", "Nagoya"]`、`needs_long_term_memory_history: false`
- 検索: 現在値・従来の記憶は0件、保留 p002 がヒット。p002 の属性（`home_location`）から現在値の川崎を渡した。変更履歴は検索していない
- 回答AIへ渡したもの: 現在値 `home_location: 川崎`（updated_at は取り消した時刻）と、保留 p002（`reopened_from: p001`）だけ
- 回答: 「名古屋の件は、現在確認待ち（保留）のまま」。保存済み（川崎）・確認待ち（名古屋の発言、p002）・未確定の点を区別した。`reopened_from` の説明から「p001 は一度確認を経て反映されたが、コマンドで取り消され、未確認に戻った。発言は撤回されていない」と述べ、「変更履歴を参照できないため、いつ確認され、いつ取り消されたかの詳細はお伝えできません」と限界を明示した。推測で補った内容は無かった
- 判断の妥当性: 「どうなった？」は今の扱い（保存されたのか、保留のままか）を聞いているとも、経緯を聞いているとも読める。今の扱いは Current と Pending で正しく答えられており、経緯の不足は回答の中で明示されたので、誤答ではない。ただし、取り消しを経た保留（`reopened_from` がある）について聞かれたのに確認・取り消しの日時や根拠が渡らないのは、経緯の説明としては不足している。この質問では、調査の2回と合わせて3回中2回、プランナーが履歴を不要と判断した
- 扱い: 今回の仕組みは「履歴が必要かは AI が判断する」ままなので、不具合ではなく残る問題として記録する（10. 残る問題）。決定的に補う案として、`reopened_from` を持つ保留や、変更履歴のある属性を渡すときに履歴も付ける、などが考えられる（未実装）

言い換え: 「引っ越しの記録ってどうなってる？」「住んでいる場所の記憶が川崎に戻ったのはなぜ？」も、プランナーの検索語は `address` / `residence` / `引っ越し` / `川崎` / `revert` などで、どちらも属性を見つけて全件を渡した。後者は「取り消しの理由は記録されていません」「確認の質問と回答は名古屋に置き換えた根拠で、取り消しの根拠ではありません」と答えた。「いつ住まいを変更した？」では、「実際に引っ越した日は記録に無い」「10:09 は確認して変更した時刻で、発言の時刻とは限らない」と区別した。

### MVP12 の状態の回帰（今の住まいは？、回答だけ実際の Claude）

B（Current と保留）、C（取り消し後）、F（保留2件）を1回ずつ。3/3 で保存済み・確認待ち・未確定の点を区別し、F では保留2件を別々の発言として示した。推測・約束・確認の質問は 0/3。B と C は「どちらか一方には断定できません」で結んだ（MVP12 から残っている言い回し。直前で「両方が有効な可能性」を述べており、二者択一の説明にはなっていない）。

### 評価用のデータの誤りと再実行

- 「14件」のケースの最初の1回は、現在値の `updated_at` を別のテスト用の値（10月1日）のまま使っていたため、履歴（10月14日）と食い違った。回答AIは「日時に食い違いがある。どちらが正しいかは判断できない」と指摘し、推測で解消しなかった。`updated_at` を直して再実行した
- 「13属性」のケースの最初の1回は、時刻をテスト用の `t00` 形式にしていたため、回答AIは「具体的な日付に直せないので順序だけを説明する」と答えた。正しい時刻にして再実行した
- 再実行で、上の「変更履歴だけでヒットした属性の Current」の問題が見つかり、修正後にもう1回実行した（表は修正後の結果）

原因は2つとも、評価の入力を一貫した1つの時計から作らず、テスト用の部品を流用したこと。

| | 原因 | 修正 |
|---|---|---|
| 14件のケース | 現在値をテスト用の `KAWASAKI`（`updated_at` が 10月1日）からコピーし、値だけ書き換えた。履歴は10月1日〜14日で作ったので、現在値の更新日時が最後の置換と食い違った | 現在値の `updated_at` を最後のイベントの日時にした |
| 13属性のケース | テスト用の `many_attributes`（時刻に意味が無いテストのため `t00` のような仮の値を使う）を、そのまま実際の Claude への入力に使った | 評価用に、1時間ずつ進む ISO 8601 の時刻で作り直した |

MVP12 でも、評価用の時計を「分を文字列で連番にする」形で作り、60分を超えて `10:65` のような時刻になった。どれも、日時を文字列で組み立てたり、テスト用の値を流用したりして、正しい日時か・前後関係が合っているかを確かめないまま Claude に渡したことが共通の原因である。

再発防止として、次を評価の手順にする（リポジトリのテスト環境は変えない）。

1. 評価用の日時は、1つの時計から `datetime` の加算で作る（文字列の連番やテスト用の仮の値を使わない）
2. Claude を呼ぶ前に、入力のすべての日時が ISO 8601 として読めること、現在値の `updated_at` が同じ属性の最後のイベントの日時と一致することを機械的に確かめる。今回この検査を作業用の領域に作り、最終の結果に使った15回の入力がすべて通り、差し替えた2回だけが検出されることを確かめた
3. テスト用の部品（`KAWASAKI`、`many_attributes` など）を評価に流用するときは、2の検査を必ず通す

テスト側では、時刻に意味の無いテストが仮の値を使うのは問題ない。将来テストでも日時の前後関係を確かめるようになったら、共通の時計（`datetime` で1分ずつ進める fixture）を `conftest.py` に置くのがよい（今回は作っていない）。

評価スクリプトと結果はリポジトリの外（作業用の領域）にある。

## 10. 残る問題

| 問題 | 内容 |
|---|---|
| 属性の起点を見つけられない | 「住まい」のように、内部の key（`home_location`）にも値にも発言にも現れない言葉だけで検索されると、属性が見つからず何も渡らない。今回は「見つからなかった」と答えさせるところまで（実際の Claude 1/1）。プランナーへ属性一覧を渡す案③で解決できる見込み |
| 履歴が必要かどうかはプランナー次第 | 「名古屋の件はどうなった？」で、プランナーが変更履歴を不要と判断すると、取り消しを経た保留についての質問でも、確認・取り消しの経緯は渡らない（調査と評価を合わせて3回中2回）。Current と Pending は渡り、回答は経緯の不足を明示したので誤答ではないが、経緯の説明としては不足（8. の「履歴が渡らなかった1問」） |
| 読み込みの失敗が回答AIに伝わらない | 履歴ファイルが読めないとき、Python と CLI の警告では区別するが、回答AIからは「見つからなかった」と同じに見える |
| 属性を特定しない質問 | 「記憶はどう変わった？」では、変更履歴でヒットした属性を新しく変わった順に3つまでしか渡さない |
| 元の発言の日時 | 確認で変わったイベントの日時は確認の日時。元の発言の日時（解決済みの保留の `created_at`）は渡していない。回答AIには「発言の日時とは限らない」と伝えるだけ |
| 1つの属性の古い履歴 | 10件を超えると古いほうを省く（最初の add が省かれる）。省いたことは伝わる |
| 番号付きの key の規則 | `_` と2以上の番号で終わる key は、別の意味でも同じ属性にまとまる（例: AI が `child_2` を独立した属性として作った場合）。抽出の指示で番号で終わる key は作らせないようにしているが、検証はしていない |
| 実際の Claude の試行回数 | 各質問・ケース1回（14件と13属性は2〜3回）。言い換えは2通りだけ |
