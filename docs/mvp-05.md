# MVP5: Working Memory（作業中ずっと見えている記憶）

## 今回解決したい問題

MVP4 で「全部の記憶を渡さず、必要な記憶を検索する」ところまでは実現した。しかし実際の仕事で、別の種類の「忘れる」が繰り返し起きた。

- 作業の最初に試験対象・試験方針を伝えていたが、大量の証跡や確認作業を進めるうちに、AI が「そもそも何を試験するのか」を忘れた。
- 最初に「商用環境・検証環境・開発環境の3環境へ展開したい」と伝えていたが、作業の途中で忘れ、最終的に開発環境向けの資産しか作らなかった。

これは長期記憶の検索だけでは解決しない。AI 自身が「昔の要求を検索する必要がある」と気付かなければ、検索そのものが行われないからである。「開発環境の資産ができました」という発言から「環境」を検索しようとは考えない。

## 目的

現在進行中の作業について、作業終了まで失われてはいけない情報（Mission / Scope / Acceptance Criteria）を、長期記憶とは別の Working Memory として保持し、検索を介さず、回答時に常に Claude へ渡す。

確認したい仮説は「すべてを検索対象にするのではなく、作業中ずっと必要な情報だけは、常時コンテキストに置いた方がよいのではないか」。

MVP5 で進めるのはこの1層の追加だけで、タスク管理システムは作らない。

## 成功条件

### 成功条件1: 作業の前提が常に渡る

1. ユーザーが「商用環境、検証環境、開発環境の3環境へ展開できる資産を作りたいです。3環境すべて揃えば完了です。」と入力する
2. Working Memory に、scope（商用環境 / 検証環境 / 開発環境）や acceptance_criteria（3環境すべて揃えば完了）などが保存される
3. 無関係な会話や作業を複数ターン行う
4. 再起動しても Working Memory が読み込まれる
5. 「ここまでで完成ですか？」と聞くと、回答用の Claude へ Working Memory が必ず渡され、3環境という条件を基準に判断できる

手動確認では、実務で起きた事故を模して「開発環境向けの資産はできました。もう完成ですか？」と聞き、商用環境・検証環境が残っていると判断できることを確認する。

### 成功条件2: 検索が0件でも渡る

長期記憶の検索が何も見つけなくても（検索しなくても）、Working Memory は回答用の Claude へ渡され、Mission / Scope / Acceptance Criteria を利用できる。

## Working Memory と Long-term Memory の違い

| | Long-term Memory | Working Memory |
|---|---|---|
| ファイル | `data/memories.jsonl` | `data/working_memory.json` |
| 中身 | 過去のユーザー発言から抽出した記憶全般 | 現在進行中の作業の Mission / Scope / Acceptance Criteria だけ |
| 回答用の Claude への渡し方 | AI が検索語を考え、ヒットしたものだけ渡す | 存在する限り、毎回すべて渡す |
| 忘れ方 | 検索しない・検索語が合わないと出てこない | 出てこないことがない |
| 量 | 増え続ける | 少数に保つ（常時コンテキストを占めるため） |
| 変更 | 追記のみ | 追加と、既存項目の置き換え |
| 構造 | 1行1記憶の JSONL | 3フィールドを持つ1つの JSON |

`conversation.jsonl`（会話原文・証拠）と `memories.jsonl`（長期記憶）の役割は MVP4 のまま変えない。Working Memory は会話履歴でも長期記憶でもない。

## AI と Python の役割分担

| 担当 | やること |
|---|---|
| AI（`claude -p`） | ユーザー発言に、現在の作業の Mission / Scope / Acceptance Criteria に当たる重要情報が含まれるかの判断。追加すべき候補・更新すべき候補を JSON で提案する。Working Memory を前提に回答する |
| Python | Working Memory の構造・フィールドの管理、候補の検証、重複の排除、状態の書き換え、保存と読み込み、回答用の Claude へ常に渡すことの制御 |

AI は状態を直接書き換えない。提案するだけで、採用するかどうかと実際の書き換えは Python が行う。MVP3 と同じく「意味の判断は AI、状態管理は Python」。

## 今回やらないこと

- Task の自動完了判定システム、チェックボックス UI
- 複数プロジェクト、複数タスク、Task ID
- Mission の階層化、Dependency 管理、Progress 管理、Next Action 管理
- 自動リマインド、Event 駆動
- relation graph、Vector DB、embedding
- 保存時の検索用 keyword 追加
- Long-term Memory の更新・superseded
- 高度な競合解消
- Working Memory の項目の削除、作業の終了・切り替え（やり直すにはファイルを削除する）
- GUI、MCP
- Claude 呼び出し回数の最適化

MVP4 の検索（AI が検索プラン → Python が単純文字列検索 → ヒットした記憶だけ渡す）は作り直さない。

## 仕様

### 保存形式

`data/working_memory.json`（UTF-8）。フィールドは `mission` / `scope` / `acceptance_criteria` の3つだけ。各項目は内容と、その根拠となったユーザー発言の抜き出しを持つ。

```json
{
  "mission": [
    {"text": "3環境へ展開できる資産を作成する", "evidence": "3環境へ展開できる資産を作りたいです"}
  ],
  "scope": [
    {"text": "商用環境", "evidence": "商用環境"},
    {"text": "検証環境", "evidence": "検証環境"},
    {"text": "開発環境", "evidence": "開発環境"}
  ],
  "acceptance_criteria": [
    {"text": "3環境すべて揃えば完了", "evidence": "3環境すべて揃えば完了です"}
  ]
}
```

- 保存場所は環境変数 `ACM_WORKING_MEMORY_FILE` で変更できる。
- `data/` は `.gitignore` の対象で、Git 管理対象外。
- 作業は1つだけ。作業を終える・やり直すときはファイルを削除する。

### 抽出

通常の AI 応答が返り、会話原文を保存できたあとに、長期記憶の抽出とは別の `claude -p` 呼び出しで行う。

入力は、現在の Working Memory と今回のユーザー発言だけ。assistant の発言や過去の会話は渡さない。Working Memory を渡すのは、既にある項目を重ねて提案させないためと、既存項目の更新を提案できるようにするため。

```text
[working memory]
Scope:
- 商用環境
[/working memory]

[utterance]
検証環境と開発環境も対象にします
```

出力は JSON 配列だけ。該当するものがなければ `[]`。

```json
[
  {"field": "scope", "text": "検証環境", "evidence": "検証環境"},
  {"field": "scope", "text": "開発環境", "evidence": "開発環境"}
]
```

既存の項目を更新する提案には、置き換える項目の文面を `replaces` に入れる。

```json
[{"field": "acceptance_criteria", "text": "3環境すべてで動作確認が取れれば完了", "evidence": "3環境すべてで動作確認が取れれば完了", "replaces": "3環境すべて揃えば完了"}]
```

雑談、質問、進捗の報告、個々の手順の指示は対象外。

### Python が行う検証

- 抽出結果全体が JSON 配列であること
- `field` が `mission` / `scope` / `acceptance_criteria` のいずれかであること
- `text` が空でない文字列であること
- `evidence` が空でない文字列で、今回のユーザー入力に部分文字列としてそのまま含まれること
- `replaces` がある場合、同じフィールドに実在する項目の文面と一致すること
- 同じフィールドに同じ内容の項目が既にあれば保存しない（大文字小文字・全角半角・空白の違いは無視）

検証を通らなかった候補は、警告を表示して保存しない。

### 通常回答時に Claude へ渡すもの

1. Working Memory（存在する限り常に、全項目）
2. 今回の検索でヒットした Long-term Memory（最大5件）
3. 今回の起動中の会話履歴
4. 現在のユーザー入力

```text
[working memory]
Mission:
- 3環境へ展開できる資産を作成する

Scope:
- 商用環境
- 検証環境
- 開発環境

Acceptance Criteria:
- 3環境すべて揃えば完了
[/working memory]

[retrieved memories]
- ユーザーの名前はテスト太郎 (origin: user, evidence: 私の名前はテスト太郎です)
[/retrieved memories]

[user]
ここまでで完成ですか？
```

過去の `conversation.jsonl` 全文と `memories.jsonl` 全件は引き続き渡さない。

システム指示で、Working Memory は現在の作業で継続的に守る必要がある条件であること、完了の判断や成果物の範囲はこれを基準にすることを伝える。

### CLI 表示

更新されたときだけ表示する。

```text
[作業記憶] scope: 商用環境 / 検証環境 / 開発環境
[作業記憶] acceptance_criteria: 3環境すべて揃えば完了
```

起動時は `作業記憶を読み込みました（5項目）。` と項目数だけ表示する。

### Claude 呼び出し回数

| 状況 | 1ターンあたり |
|---|---|
| 長期記憶がまだ1件も無い | 3回（通常回答・長期記憶の抽出・作業記憶の抽出） |
| 通常 | 4回（検索プラン作成・通常回答・長期記憶の抽出・作業記憶の抽出） |
| 1回目の検索が0件 | 5回（上記 + 検索語再生成） |

### エラー処理

Working Memory の抽出はチャット本体より優先度が低い。次の場合は警告を表示して会話を続ける。

| 状況 | 動作 |
|---|---|
| 抽出の Claude 呼び出しが失敗 | 警告を表示。そのターンは更新しない |
| 抽出結果が不正な JSON | 警告を表示。そのターンは更新しない |
| 候補が検証を通らない | 警告を表示。その候補だけ保存しない |
| `working_memory.json` の保存に失敗 | 警告を表示。そのターンは更新しない（メモリ上の状態も変えない） |
| 起動時に `working_memory.json` が壊れている | エラーを表示して終了。ファイルは変更しない |

## 評価方法

- 自動テスト（pytest）: `subprocess` / Claude をモックし、保存先は `tmp_path` を使う。Working Memory が回答用プロンプトに常に含まれることを確認する。
- 手動スモークテスト: 成功条件1の流れを実際の `claude` で実行し、「この作業の対象環境は？」と「開発環境向けの資産はできました。もう完成ですか？」への回答を確認する。
