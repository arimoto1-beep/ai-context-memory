# MVP15: 記憶抽出の入力削減と自動追加の安全性確保

状態: **実装済み・未コミット**。基準は MVP14（コミット `a2622ba`、タグ `article-16`）

## 1. 目的と対象範囲

「忘れないAI」は、Python が記憶を保持し、必要な情報だけを AI へ渡す構造で、保存できる記憶の量を AI のコンテキスト長から切り離している。MVP15 の調査で、構造化長期記憶の抽出 AI（既存の値との関係を判断する AI）だけは、毎ターン現在値（Current）の全量を受け取っており、記憶が増えるほど入力が際限なく増えることが分かった。

ただし、入力を減らして関係する既存の属性を AI が見落とすと、同じ意味の属性が別の key で**確定追加**される（`home_location = 川崎` があるのに `residence = 名古屋` が追加される）ことも、実際の Claude で確かめた。

MVP15 では次の3つを入れた。最優先は入力の削減ではなく、**入力を減らしても記憶の整合性を壊さないこと**。

1. AI 呼び出しごとの入力サイズと usage の記録
2. 新しい key の自動追加に対する Python 側の安全策
3. 属性数に応じた、抽出 AI への入力の切り替え（全量 / key の一覧と一部の値 / 一部の値）

### 今回やらないこと

記憶エフォート（Low / Medium / High）の切り替え、ベクトル検索、同義 key の自動統合、数千属性向けの索引構造、回答 AI の会話履歴の上限、番号付き key の値の上限、Claude CLI 内部の Haiku 呼び出しへの対策（10 に次の候補として整理した）。

### 記憶量と入力サイズ（実装前）

Claude は呼ばず、実際のコードでプロンプトを組み立てて測った（`ClaudeCLI` の呼び出し部分だけを差し替え）。評価データは一時ディレクトリに作り、日時を検査した（タイムゾーン付き・範囲内・変更履歴が時系列順・保留が対象の更新より後）。値の種類は short（短い値だけ）と mixed（約半数が60文字前後の文）。評価データの key は約25文字で、実際の key より長い。

**文字数は実測。トークン数は推定**で、実際の Claude の usage 68件から当てはめた換算式（非ASCII文字×1.053 ＋ ASCII文字×0.478 ＋ 410、68件での誤差は最大1%）による。

| 属性数 | 抽出 AI の入力（short） | 抽出 AI の入力（mixed） |
|---|---|---|
| 10 | 3,454文字（推定 約3,400トークン） | 3,608文字（推定 約3,500） |
| 100 | 6,188文字（推定 約4,800） | 8,246文字（**実測 6,970前後**） |
| 1,000 | 33,886文字（推定 約19,000） | 52,822文字（推定 約39,000） |
| 5,000 | 156,591文字（推定 約82,000） | 251,064文字（推定 約182,000） |

ほかの AI の入力は属性数に比例しなかった。

| AI | 入力（100属性・mixed） |
|---|---|
| 検索プランナー | 6,620文字（100属性を超えると一覧を渡さないため 4,082文字） |
| 回答 AI | 約9,300文字 |
| 作業記憶の抽出 | 1,615文字 |
| 従来の記憶の抽出 | 488文字 |

1ターンの推定トークン数に抽出 AI が占める割合は、100属性で約30%、1,000属性で約72%、5,000属性で約92%。保留1,000件、変更履歴11,000件でも、回答 AI への入力は上限で止まった（+1.1千、+1.6千文字）。ただし、同じ属性の値50個で約16千文字、会話50往復で約27千文字と、どちらも上限なく増えた。

Python 側の検索・整形は、5,000属性・変更履歴11,000件でも最大0.18秒だった。

### 抽出 AI に全量が必要か（実際の Claude、68回）

100属性（mixed）・7発言・5条件・各2回。68回とも正常に終わり、生の出力はすべて試行ごとに保存した。AI の出力は、本番と同じ `apply_candidates` に**現在値の全量**を渡して判定した。

| 条件 | AI へ渡したもの | 正しい属性 | 意味が重複する属性の自動追加 | 誤った上書き | 入力（実測平均） |
|---|---|---|---|---|---|
| A 全量（現行） | 全100属性の値 | 12/12 | 0 | 0 | 6,973トークン |
| S 関係する属性が見つかった | 関係する属性を含む10属性の値 | 12/12 | 0 | 0 | 3,593 |
| **M 関係する属性を取りこぼした** | 関係しない10属性の値 | **0/12** | **6/12** | 0 | 3,626 |
| **MN M に「一部だけです」と伝えた** | M と同じ＋注意書き | **0/12** | **6/12** | 0 | 3,752 |
| BK key の一覧と関係しない値 | 全100属性の key と、関係しない10属性の値 | 12/12 | 0 | 0 | 5,102 |

「12」は、関係する属性がある6発言 × 2回（複数の属性にまたがる発言は1回と数えた）。

**重要な失敗例（M・MN）**

- 「今は名古屋に住んでいます」「川崎から名古屋に引っ越しました」で、AI は `residence = 名古屋` を新しい属性として coexist と判断した。Python はそのまま追加し、`home_location = 川崎` と `residence = 名古屋` が、どちらも確定した値として並んだ。保留にならないので、関係が分からないという情報そのものが失われる
- 勤務先・趣味・既存の key 名を変えた発言は保留になったが、安全だったからではない。AI が作った key が偶然既存の key と同じで、衝突として保留になっただけだった
- 「一部だけです」という注意書き（MN）は、関係する12回すべてで M と同じ出力だった。**「関係する記憶がない」と「見つけられなかった」の区別は、AI への注意書きでは守れなかった**

**分かったこと**

- 置き換えの検証は、Python が全量の現在値に対して行っている。BK では AI は「川崎」を見ていなかったが、「川崎から名古屋に引っ越しました」は正しく置き換わり、「今は名古屋に住んでいます」は保留になった。置き換えの経路は、入力を減らしても誤った上書きにならない
- 守りが無かったのは、coexist で新しい key を追加する経路（`apply_candidates` の最後）だけだった
- 判断に必要だったのは key の一覧で、値は必須ではなかった

## 3. AI 呼び出しの記録（`llm.ClaudeCLI`）

`ClaudeCLI._run` が、成否にかかわらず呼び出し1回ごとに1件を記録する。記録はメモリ上の `ClaudeCLI.calls` に残る。`call_log_path` があれば JSONL へも追記する。CLI の既定は `data/ai_calls.jsonl` で、`ACM_AI_CALL_LOG_FILE` で変えられる。

| 項目 | 内容 |
|---|---|
| `role` | `search_plan` / `answer` / `memory_extraction` / `structured_memory_extraction` / `working_memory_extraction` / `confirmation_judgment` |
| `turn` | 入力のターンの番号（`ChatSession.begin_turn` が CLI の入力1つごとに進める） |
| `system_chars` / `prompt_chars` / `input_chars` | 指示・入力・合計の文字数（実測） |
| `status` / `error_kind` | `ok` / `error`。`not_found` / `timeout` / `launch_failed` / `not_logged_in` / `exit_error` / `no_text` |
| `elapsed_ms` | Python で測った所要時間 |
| `duration_ms` / `duration_api_ms` | `claude -p` の出力にあった値（無ければ null） |
| `usage` | `input_tokens`・`cache_creation_input_tokens`・`cache_read_input_tokens`・`output_tokens`（報告された値だけ。無い項目は null）と、入力3項目がすべて報告されたときだけの合計 `input_tokens_total` |
| `model_usage` | `modelUsage` のモデルごとの入力・出力・キャッシュのトークン数。**出力にあったモデル名のまま記録し、役割の分類はしない**（内部の Haiku 呼び出しの目的は確認していないため） |
| `details` | 抽出 AI だけ。渡した範囲（`view`）、key の一覧の完全性、属性数、一覧に載せた属性数、値を渡した属性数 |

- **usage が無いときは null にし、推定値は入れない**
- 記録には、プロンプト・応答の本文と、エラーの詳細（応答の本文を含みうる）を入れない。モデル名・数・状態の名前だけを入れる
- 記録のために AI の呼び出しは増えない（テストで、2ターンの記録10件と実際の呼び出し10回が一致することを確かめた）
- ファイルへ書けなくても呼び出しは止めない。CLI は一度だけ警告を表示する。記録の失敗（ファイルを開けない・書けないほか、記録先の型の誤りなど）は呼び出しの結果を変えない（成功は成功、失敗は元の `LLMError` のまま。テストで固定）
- `data/ai_calls.jsonl` は `.gitignore` の `data/` に含まれ、Git の管理対象にならない（`git check-ignore` で確認）
- 記録は追記だけで、ローテーションや削除はしない。1件は数百バイトで、1ターン5件なので、1日100ターンで年に数十MB程度になる見込み（推定）。上限や整理は今後の課題（10）

## 4. 抽出 AI へ渡す範囲（`structured_memory.extraction_view`）

範囲は、現在値の属性数（番号付きの key は番号の無い key にまとめた数）で決める。

| 属性数 | 範囲（`mode`） | 抽出 AI へ渡すもの | key の一覧の完全性 |
|---|---|---|---|
| 〜100（`EXTRACTION_FULL_MAX_ATTRIBUTES`） | `full` | **従来と同じ**（指示も入力も1文字も変えない） | complete |
| 101〜300（`EXTRACTION_KEY_LIST_MAX_ATTRIBUTES`） | `keys` | 範囲の説明、すべての属性の key の一覧（値なし）、一部の属性の値 | complete |
| 301〜 | `selected` | 範囲の説明、一部の属性の値（key の一覧は渡さない） | partial |

`keys` と `selected` で値を渡す属性は、次の順で最大15属性（`EXTRACTION_MAX_VALUE_ATTRIBUTES`）。

1. **発言に値がそのまま現れる属性（上限に関係なく必ず渡す）**。置き換えを自動で実行できるのは、既存の値が発言に現れるときだけ（`replace_hold_reason`）なので、自動で置き換わりうる属性の値は必ず AI に見えている。照合は置き換えの検証と同じ正規化（大文字小文字・全角半角）で行う
2. 検索プランナーが選んだ属性（`Retrieval.selected_attributes`）
3. 検索語に一致した属性（`Retrieval.query_attributes`。MVP15 で追加）
4. 未解決の保留の属性（新しい保留から）

### 発言に値が現れる属性に上限が無いことの影響

1 は上限を設けていない（切り捨てると、自動で置き換わりうる属性の値が AI に見えなくなるため）。短い値や共通の値が多くの属性にあると、その分だけ入力が大きくなる。照合は部分一致なので、「あり」という値は「ありがとう」にも一致する。

最終確認で、関係しない属性の値（約25文字の key）を共通の短い値に置き換えて測った（AI は呼んでいない。文字数は実測）。

| 属性数 | 共通の値を持つ属性 | 発言 | 値を渡した属性 | 抽出 AI の入力 |
|---|---|---|---|---|
| 300 | なし | 今日は晴れです。 | 0 | 10,470文字 |
| 5,000 | なし | 今日は晴れです。 | 0 | 3,830文字 |
| 300 | 50（「あり」「はい」「1」） | ありがとう。1つ聞きたいです。 | 33 | 11,302文字 |
| 5,000 | 500（同上） | 同上 | 333 | 12,313文字 |
| 5,000 | 2,000（同上） | 同上 | 1,333 | 37,814文字 |
| 5,000 | 300（「東京」） | 東京に行きました。 | 300 | 11,615文字 |
| 5,000 | 5,000（「1」「2」「3」） | 123 | 5,000 | 128,810文字 |

- 入力は、発言に値が現れる属性の数にほぼ比例して増える（1属性あたり約25文字）
- 最悪の場合（すべての値が発言に現れる）は、全量を渡すのとほぼ同じ大きさになる。全量より大きくはならない（`selected` では key の一覧を渡さないため）
- **制約として残す**。誤った上書きを許さない条件（置き換えには既存の値が発言に現れ、終了の表現があること）を保つため、件数の切り捨ては行わない
- 短い値の部分一致で選ばれた属性は、AI に値が見えるだけで、置き換えの検証は変わらない

`keys` と `selected` のときだけ、抽出 AI の指示の末尾に `STRUCTURED_MEMORY_VIEW_NOTICE` を足す。内容は「値は一部だけ」「一覧に同じ意味の属性があれば、その key を使う」「見当たらないことは保存されていないことを意味しない」。ただし、調査で注意書きだけでは重複を防げなかったので、**安全性は 5 の Python 側で確保する**。

### しきい値の決め方

| 属性数 | 全量（short / mixed） | `keys`（short / mixed） |
|---|---|---|
| 51 | 4,695 / 5,922文字 | 5,174 / 5,174（+10% / −13%） |
| 100 | 6,188 / 8,246 | 6,469 / 6,469（+5% / −22%） |
| 150 | 7,807 / 11,035 | 7,890 / 7,890（+1% / −28%） |
| 300 | 12,392 / 17,936 | 11,859 / 11,859（−4% / −34%） |

- 評価データ（key 約25文字）では、値の短い記憶は100属性まで、key の一覧のほうが全量より大きかった。全量は、MVP9〜14 の評価をすべて行ってきた経路でもある。依頼の候補（全量は50属性まで）は採らず、**100属性までは全量のまま**にした
- key の一覧の上限は300属性にした。300属性の一覧での判断は実際の Claude で確かめた（7）。それを超える一覧での判断は評価していない
- 2つのしきい値は別の定数で、テストで「全量の上限 < 一覧の上限」と境界の値（100 / 101 / 300 / 301）を固定した

## 5. 新しい key の自動追加の安全策

抽出 AI へ渡した範囲とは別に、Python が「AI へ渡した key の一覧が、保存されている属性のすべてか」を判定する（`key_coverage`）。

| `key_coverage` | 条件 | 新しい key の追加 | 置き換え |
|---|---|---|---|
| `complete` | 全量か全属性の key の一覧を渡し、保存されている現在値がセッションの現在値と同じだと確かめた | 従来どおり自動で追加 | 従来どおり（検証を通れば実行） |
| `partial` | 属性が300を超え、一覧を渡していない | **追加せず保留** | 従来どおり（検証を通れば実行） |
| `unavailable` | 保存されている現在値を読めない、またはセッションの外で変わった | **追加せず保留** | **実行せず保留** |

- 保存されている現在値は、抽出の前に毎回読み直して、セッションの現在値と比べる（5,000属性でも数十ms）
- `unavailable` のときに置き換えも止めるのは、このセッションの現在値で、保存されている内容（壊れたファイルや外部の変更）を上書きしないため。`/confirm` と `/revert` は MVP10・11 から、この状態では実行しない
- 検証（`apply_candidates`）には、AI へ見せた範囲によらず、**常に現在値の全量**を渡す
- 安全策は自動の反映を**減らすだけで増やさない**。7種類の判断の組み合わせ × 3種類の保留のかけ方の21通りで、保留をかけたときに反映されるものは、かけないときに反映されるものの部分集合で、保留の数は減らないことをテストで固定した

**限界（解決していない）**: key の一覧が完全（`complete`）でも、AI が同じ意味の別の key（`residence`）を作れば、Python は意味の重複を見分けられず、追加する。全量を渡していた MVP14 までと同じ限界で、テスト `test_known_limit_a_synonym_key_is_added_when_the_key_list_is_complete` で現状として固定した。

## 6. 保留の扱いと確認

新しい key を保留にするときは、既存の保留と同じ形式（`_held`）で保存する。

- 発言・提案された key と値・AI の判断・保留の理由を残す
- 保存形式・ファイルは変えていない
- 保留は回答 AI へ渡り、`/pending` に表示される

確認できるかどうかは、保留に `target_key` があるかで分かれる。

| 保留 | `/confirm` |
|---|---|
| `target_key` が無い（AI が関係する既存の属性を挙げなかった。`residence = 名古屋` など） | **確認できない**。MVP10 からの規則「既存の項目に関係しない保留は確認できない」による。保留は消えず、現在値も変わらない（テストで固定） |
| `target_key` がある（AI が既存の属性を挙げた） | 従来どおり確認できる。共存なら番号付きの key（`hobby_2`）、置換なら y/N の後で置き換え。取り消しも従来どおり |

**機能上の未解決課題（今回は変えていない）**

`target_key` の無い保留には、解決する手段が無い。これは性能の制約ではなく、**保留を作っても確定できないという機能上の未解決課題**である。確認・取り消しの意味を変える必要があるため、今回は手を入れなかった。

最終確認で、次をテストで確かめた（`test_unresolvable_held_new_key_is_shown_as_such_and_survives_a_restart` ほか）。

- 発言・提案された key と値・保留の理由が保留ファイルに保存される
- 現在値は変わらない
- `/pending` に内容と「確認できません: 既存の項目（target_key）に関係しない保留は、MVP10 では確認できません」が表示される
- 再起動しても保留は失われず、`/pending` で見える
- 保留を作ったときの表示: AI が確認の質問を付けていても「`/confirm` で確認できます」とは案内せず、「既存の項目に関係しないため、/confirm では確定できません」と表示する（最終確認で修正した表示。確認の処理は変えていない）

- 300属性を超える記憶では、まったく新しい属性（「好きな映画はローマの休日です」）も保留になる（実際の Claude で 2/2）
- この保留はたまっていく
- 解決するには、「新しい属性として追加する／既存の属性 X と同じ」を確認する仕組みが必要になる
- 発言は保留ファイルと会話原文に残っており、失われない

このほか、次の制約がある。

- 共存で確認した値は、AI が提案した key ではなく `target_key` の番号付きの key になる（MVP10 からの規則）
- 保留の保存先が設定されていないセッション（CLI では常に設定される）では、保留にした提案は保存されない（MVP9 からの動作）

## 10. 残る問題と次の MVP 候補

| 問題 | 内容 |
|---|---|
| 同じ意味の別の key | 一覧が完全でも、AI が別の key を作れば追加される（5 の限界）。同義 key の統合は未実装 |

## 11. 評価の手順（生の出力の保存）

評価スクリプトは、リポジトリの外の作業用ディレクトリに置いた。MVP14 で子プロセスの文字コードにより結果を失った件（`docs/mvp-14.md` の 8）を踏まえ、次のようにした。

- `claude` を直接起動し、標準出力・標準エラーをバイト列のまま、**解析より前に**試行ごとのファイルへ保存した
- 試行ごとに、実行 ID・開始時刻・コードの版・条件・状態（`ok` / `error` / `timeout`）を記録した
- 集計は保存したファイルからだけ行った
- 1つの試行の失敗で残りを止めない作りにした

**実際の Claude の呼び出しは、動作確認1回、調査68回、実装後の比較45回の計114回。失った結果は無い。** リポジトリには集計結果だけを載せた。生の出力・プロンプトは含めていない。
