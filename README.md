# ai-context-memory

「忘れないAI」を段階的に作っていくPoCです。

## 現在の状態: MVP9（記憶の誤上書きを防ぎ、Pending を導入する）

AI が判断を間違えても、既存の記憶を不用意に壊さず、新しい発言も失わないようにする段階です。評価条件と、事前実験（実際の Claude で121回）の結果は [docs/mvp-09.md](docs/mvp-09.md) にあります。

MVP8 では、AI が同じ key だと判断すると、Python が機械的に現在値を置き換えていました。そのため、現在値が `user.home_location = 川崎` のときに「単身赴任で、平日は名古屋に住んでいます。」と言うと、川崎が「平日は名古屋」で上書きされることがありました。**同じ属性であることと、既存の値を上書きしてよいことは、別の判断です。**

- AI が、新しい発言と既存の値の関係を replace / coexist / pending / no_change で判断する。MVP8 の構造化抽出の Claude 呼び出しを置き換えたもので、呼び出し回数は増えていない
- **AI が replace と言っただけでは、Python は上書きしない。** 新しい値が発言にそのまま現れること、既存の値の終了・訂正を述べた部分（AI が発言から抜き出したもの）が発言に一字一句あり、その中に既存の値と、終了・変更・訂正を表す表現（15個の短い一覧）があることを Python が確かめられたときだけ置き換える。**これは文字列の確認で、意味の検証ではない**
- AI の自己申告（「既存の値は終わったと明示されている」など）は、置き換えを止める方向にだけ使い、許可の根拠にはしない。事前実験で、AI は誤った replace と同時に、それを正当化する申告も返したため
- 確かめられない置き換えや、既存の key との衝突は、捨てずに Pending（保留）へ格下げする。Pending は Current とは別のファイル（`data/long_term_memory_pending.json`）に保存され、再起動後も残る
- **Pending は「新しい発言が疑わしい」という意味ではない。** 「名古屋に住んでいる」という発言は確実にあり、分からないのは川崎の住まいとの関係だけである。新しい情報を保存することと、既存の値を無効にすることを分けた
- 回答時は、Current の検索でヒットした key に関係する Pending も一緒に渡す。回答用の Claude には、古い Current だけで断定しない・Pending を確定した値として扱わない・分からないことは分けて伝える、と指示している
- Pending の確認質問は表示するだけで、ユーザーの回答から Pending を確定する処理はまだ無い（次の MVP 候補）
- 関係判断の出力の前に推論文が漏れて JSON の解析に失敗することがあったので、出力の末尾にある唯一の JSON だけを安全に取り出すようにした（取り出しても検証はすべて行う）
- Current と History の保存形式は MVP8 と同じ。既存データの migration はしていない

| 役割 | 担当 |
|---|---|
| key の意味判断、既存の値と新しい発言の関係の判断、確認質問 | AI |
| 判断の検証、置き換えてよいかの確認、Pending への格下げ、保存 | Python |

MVP8 の内容（Long-term Memory に current / history を持たせる）は、同じ key・違う value の扱いを除いて変わっていません。評価条件は [docs/mvp-08.md](docs/mvp-08.md) にあります。

MVP7 までの Long-term Memory（`memories.jsonl`）は追記のみで、「好きな果物は梨」と「最近は好きな果物はりんご」が両方残るだけでした。どちらが現在の値なのかは、ファイルからは分かりませんでした。

- Long-term Memory に、構造化した現在値（current）を別レイヤーとして追加した（`data/long_term_memory_state.json`）
- 発言が「誰の（subject）、何という属性（key）の、どんな値（value）か」は AI が分類する。key は `favorite_fruit` のような英語の snake_case で、AI が意味を判断して決める。Python にキーワードの対応表は無い
- AI には現在ある subject / key / value を見せ、同じ意味の属性なら既存の key を再利用させる
- AI は候補を出すだけで、状態遷移は指定しない。同じ subject + key に新しい value が来たら、Python が current を更新する（current に無ければ add、同じ value なら何もしない、違う value なら replace）。MVP9 で、違う value でも自動では replace しないようにした
- 置き換えられた古い value は、変更履歴（history）へ残す（`data/long_term_memory_history.jsonl`）。current は「今有効な値」、history は「どう変わったか」で、役割を分けている
- 従来の `memories.jsonl`（legacy）はまだ残している。形式も抽出も検索も変えておらず、MVP8 より前の記憶の移行（migration / backfill）もしていない。同じ内容が両方に入ることは許容している
- current は毎回すべては渡さない。検索プランナーが Long-term Memory を必要と判断したとき、同じ検索語で legacy と current の両方を検索し、ヒットしたものだけを渡す
- current と legacy の記憶が矛盾したら、current を優先するよう回答用の Claude に指示している
- 過去の値が必要かどうかも、既存の検索プランナー1回の中で AI が判断する。必要なときだけ history を検索し、ヒットしたイベントだけを古い順に渡す
- 更新（好みが変わった）と訂正（言い間違いだった）と別物の区別はまだしない。同じ subject + key に違う value が来たら、どれも replace として扱う（MVP9 で、別物は coexist、関係が分からないものは Pending になった）
- subject は `user` だけ。Long-term Memory の remove もまだ無い
- 構造化抽出の分、Claude Code の呼び出しは1ターンあたり1回増えた（通常5回）

| 役割 | 担当 |
|---|---|
| key の意味判断（同じ属性か、別の属性か） | AI |
| 状態遷移（add / replace / 変更なし）、検証、保存 | Python |

MVP7 の内容（Working Memory History を必要なときだけ検索する）は変わっていません。評価条件は [docs/mvp-07.md](docs/mvp-07.md) にあります。

MVP6 では Working Memory の変更履歴を残すだけで、回答用の Claude へは渡していませんでした。そのため「ステージング環境を戻す直前の対象環境は？」に正しく答えられても、「履歴を見たわけではなく推定です」という回答になっていました。

- Working Memory History（`data/working_memory_history.jsonl`）を、必要なときだけ検索するようにした
- Current Working Memory は現在状態として、これまでどおり常に全項目を渡す
- History は「作業状態がいつ・どう変わったか」を知るために使う。現在状態としては扱わない
- Long-term Memory（ユーザーが過去に述べたこと・決めたこと。日時なし）とは役割が異なる
- どの記憶ソースを使うかは AI が判断する。MVP4 の検索プランナーを拡張し、1回の呼び出しで Long-term Memory と History の両方について、必要かどうかと検索語を決めさせる。判断材料として Current Working Memory を検索プランナーにも見せる
- Python は AI が出した検索プランを実行するだけ。「直前」「いつ」のような語を Python が解釈して分岐することはしない
- History 全文は毎回は渡さない。検索でヒットしたイベントだけ（最大10件）を、古い順に並べて渡す
- 過去のある時点の状態を Python で再構築すること（State Replay）はまだ行わない。現在状態と取得したイベントから過去の状態を読み取るのは AI の役割
- History の検索は Python の処理なので、Claude Code の呼び出し回数は MVP6 から増えない

| 記憶ソース | 答える問い | Claude へ渡すとき |
|---|---|---|
| Current Working Memory | 作業が今どうなっているか | 常に全項目 |
| Working Memory History | 作業状態がいつ・どう変わったか | AI が必要と判断し、検索でヒットしたものだけ |
| Long-term Memory の current（MVP8） | ユーザーについて、今有効な値は何か | AI が必要と判断し、検索でヒットしたものだけ |
| Long-term Memory History（MVP8） | ユーザーについての値がいつ・どう変わったか | AI が必要と判断し、検索でヒットしたものだけ |
| Long-term Memory の Pending（MVP9） | ユーザーが述べたが、既存の値との関係がまだ確認できていないこと | current と同じ検索でヒットしたもの、ヒットした current の key に関係するもの |
| Long-term Memory の legacy（`memories.jsonl`） | ユーザーが過去に何を述べたか・決めたか（古い内容も混ざる） | AI が必要と判断し、検索でヒットしたものだけ |

MVP6 の内容（Working Memory から正しく忘れる）は、履歴の扱いを除いて変わっていません。評価条件は [docs/mvp-06.md](docs/mvp-06.md) にあります。

MVP5 の Working Memory は追加と置き換えしかできず、「ステージング環境はやっぱり対象外にします」と言うと、scope の「ステージング環境を対象とする」が「ステージング環境は対象外とする」に置き換わり、対象範囲の一覧に否定情報が残っていました。

- Working Memory に remove を追加した。状態変更は add / replace / remove の3つ
- 「Xは対象外にする」「Xはもう不要」「Xを外す」のような明示的な発言で、現在状態から該当項目を削除できる。否定文を項目として残さない
- AI は削除候補（`operation: "remove"` と削除する既存項目の文面 `target`）を提案するだけ。Python が field・evidence・target の実在と一意性を確認してから削除する。部分一致や似た項目では削除しない
- 削除しても変更履歴は `data/working_memory_history.jsonl` に別に残す（現在状態からは消す / 過去に存在したことは履歴に残す）
- 現在状態として回答用の Claude へ渡すのは `working_memory.json` の内容だけ。削除済みの項目は現在状態には含めない（履歴は MVP7 で、必要なときだけ検索して渡すようになった）
- Long-term Memory は過去の経緯を残したまま（MVP4 のまま変えない）。回答用の Claude には、Working Memory を現在有効な状態として、長期記憶と矛盾したら Working Memory を優先するよう指示する
- scope を変えても完了条件（acceptance_criteria）は連動して更新しない。食い違いが残った場合は、AI がその不整合を指摘する
- Claude Code の呼び出し回数は MVP5 から変わらない

MVP5 の内容（Working Memory の追加）は変わっていません。評価条件は [docs/mvp-05.md](docs/mvp-05.md) にあります。

- Long-term Memory（長期記憶）と Working Memory（作業記憶）を分離した
- Long-term Memory は検索して使う（MVP4 のまま）
- Working Memory は検索せず、存在する限り毎回すべて回答用の Claude へ渡す
- Working Memory に入れるのは、現在進行中の作業の Mission / Scope / Acceptance Criteria の3種類だけ
- AI がユーザー発言から候補を提案し、Python が検証して保存する。AI は状態を直接書き換えない
- Working Memory は `data/working_memory.json` に保存され、再起動後も残る
- まだタスク管理システムではない。進捗・次の作業・完了判定・複数タスクは扱わない
- 1ターンあたりの Claude Code 呼び出しは通常4回（検索プラン作成・通常回答・長期記憶の抽出・作業記憶の抽出）、検索が0件なら5回

MVP4 までの内容も変わっていません。

- CLIでAIと会話できる
- 会話原文は `data/conversation.jsonl` へ保存する。これは証拠として残すだけで、再起動後に Claude へ再送しない
- ユーザー発言から抽出した長期記憶を `data/memories.jsonl` へ保存する（記憶抽出は MVP3 の方式のまま。対象はユーザー発言だけ）
- 全記憶を毎回 Claude へ渡すのをやめた
- 現在の質問から AI（Claude）が検索語を作り、Python が `memories.jsonl` を単純に文字列検索する
- ヒットした記憶だけ（最大5件）を、会話履歴とは別枠で回答用の Claude へ渡す
- 1件もヒットしなければ、1回だけ検索語を変えて再試行する（最大2ラウンド）
- ベクトル検索・embedding・全文検索エンジンはまだ使っていない。現段階の検索は単純な部分一致である
- `memories.jsonl` 自体には、更新・矛盾解消はまだない（MVP8 で、現在値を別レイヤーとして持つようにした）

これまでの段階:

| | 内容 |
|---|---|
| MVP1 | 履歴をメモリ上にだけ持つ「普通のAIチャット」。終了すると忘れる |
| MVP2 | 会話をファイルへ保存し、再起動時に全履歴を Claude へ再送する（[docs/mvp-02.md](docs/mvp-02.md)） |
| MVP3 | 会話原文と長期記憶を分離し、再起動後は長期記憶の全件を渡す（[docs/mvp-03.md](docs/mvp-03.md)） |
| MVP4 | AI が考えた検索語で長期記憶を検索し、ヒットした記憶だけを渡す（[docs/mvp-04.md](docs/mvp-04.md)） |
| MVP5 | 作業の Mission / Scope / Acceptance Criteria を Working Memory として保持し、常に渡す（[docs/mvp-05.md](docs/mvp-05.md)） |
| MVP6 | Working Memory から項目を remove できるようにし、変更履歴を現在状態と分けて残す（[docs/mvp-06.md](docs/mvp-06.md)） |
| MVP7 | Working Memory の変更履歴を、AI が必要と判断したときだけ検索して渡す（[docs/mvp-07.md](docs/mvp-07.md)） |
| MVP8 | Long-term Memory の一部を subject / key / value で持ち、現在値と変更履歴を分ける（[docs/mvp-08.md](docs/mvp-08.md)） |
| MVP9 | AI が既存の値と新しい発言の関係を判断し、Python は確かめられる置き換えだけを実行する。残りは Pending として保存し、回答時に参照する（[docs/mvp-09.md](docs/mvp-09.md)） |

## セットアップ

Python 3.10 以上と、ログイン済みの [Claude Code](https://claude.com/claude-code) CLI が必要です。

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
```

LLMの呼び出しには `claude` コマンドを非対話モード（`claude -p`）で使います。APIキーは不要で、Claude Code にログインしているサブスクリプションの利用枠を消費します。

```powershell
claude auth status   # "loggedIn": true, "authMethod": "claude.ai" なら準備完了
claude auth login    # 未ログインの場合
```

環境変数 `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` が設定されていても、このアプリは `claude` に渡しません（渡すとAPI課金になるため）。

## 起動方法

```powershell
python -m ai_context_memory
```

`exit` または `quit`（もしくは Ctrl+C / Ctrl+Z → Enter）で終了します。

```text
チャットを開始します。終了するには exit または quit と入力してください。

あなた> 私の名前はテスト太郎です

AI> テスト太郎さん、はじめまして。
[記憶] ユーザーの名前はテスト太郎

あなた> exit
終了します。
```

`[記憶]` は、その発言から長期記憶として保存した内容です。

再起動すると、長期記憶を検索対象として読み込みます。前回の会話そのものも、記憶の全件も Claude へは渡しません。質問のたびに検索し、ヒットした記憶だけを渡します。

```text
長期記憶を読み込みました（4 件）。
チャットを開始します。終了するには exit または quit と入力してください。

あなた> 私の名前は？
[検索] 名前 / 氏名
[検索結果] 1件

AI> テスト太郎さんです。

あなた> 私の血液型は？
[検索] 血液型
[検索結果] 0件
[再検索] O型 / A型 / B型
[検索結果] 0件

AI> 血液型については記録が見当たらず、覚えていません。

あなた> 1+1は？

AI> 2です。
```

`[検索]` は AI が考えた検索語（複数あるときは ` / ` 区切り）、`[検索結果]` はヒットした記憶の件数です。過去の記憶が不要だと AI が判断した発言では、検索しません。

作業の目的・対象・完了条件を伝えると、長期記憶とは別に作業記憶へ保存されます。`[作業記憶]` は、その発言で作業記憶に追加・置き換え・削除した内容です。

```text
あなた> 今回の作業では商用環境、検証環境、開発環境の3環境へ展開できる資産を作ります。3環境すべての資産が揃えば完了です。

AI> 承知しました。…
[作業記憶] mission: 3環境へ展開できる資産を作る
[作業記憶] scope: 商用環境 / 検証環境 / 開発環境
[作業記憶] acceptance_criteria: 3環境すべての資産が揃っていること
```

作業記憶は再起動後も読み込まれ、検索の結果に関係なく毎回 Claude へ渡されます。

```text
長期記憶を読み込みました（1 件）。
作業記憶を読み込みました（5項目）。
チャットを開始します。終了するには exit または quit と入力してください。

あなた> 開発環境向けの資産はできました。もう完成ですか？
[検索] 開発環境 / 本番環境 / 資産
[検索結果] 0件
[再検索] 成果物 / デプロイ / 完成
[検索結果] 0件

AI> まだ完成ではありません。完了条件は「3環境すべての資産が揃っていること」なので、商用環境向け・検証環境向けの資産が不足しています。…
```

対象を入れ替えたり外したりすると、作業記憶の現在状態が書き換わります。外した項目は作業記憶から消え、以後 Claude へは渡されません。

```text
あなた> 検証環境の代わりにステージング環境を対象にします。

AI> 承知しました。…
[作業記憶] scope: 検証環境 → ステージング環境

あなた> ステージング環境はやっぱり対象外にします。

AI> 承知しました。ステージング環境を対象から外します。…ただ、完了条件は「3環境すべて」のままなので、対象の数と合わなくなっています。…
[作業記憶] scope: ステージング環境 → 削除
```

完了条件は自動では書き換えません。対象範囲と完了条件が食い違ったときは、AI がその不整合を指摘します。

過去の変更について聞くと、作業記憶の変更履歴を検索してから回答します。検索したターンにだけ `[履歴検索]` と `[履歴検索結果]` が表示されます（イベントの中身は表示しません）。現在の状態を聞いただけのターンでは検索しません。

```text
あなた> この作業の対象環境は？

AI> 商用環境、開発環境、ステージング環境の3つです。

あなた> ステージング環境を戻す直前の対象環境は何でしたか？
[履歴検索] ステージング / scope / 環境
[履歴検索結果] 7件

AI> 商用環境と開発環境の2つでした。19:08:02 にステージング環境が対象外になり、19:08:24 に対象へ戻されています。
```

使用モデルは Claude Code 側の既定モデルです。環境変数 `ACM_MODEL` で変更できます（`claude --model` に渡せる値）。検索プラン作成・通常回答・長期記憶の抽出・長期状態の抽出・作業記憶の抽出のすべてに同じモデルを使います。

```powershell
$env:ACM_MODEL = "sonnet"
```

`claude` はツール無効・利用者設定（CLAUDE.md、MCP、フックなど）を読み込まないモードで起動するため、素のチャットとして動作します。1ターンごとに `claude` を次の回数だけ起動するので、応答が表示されるまでと、表示されたあと次の入力ができるまでに、それぞれ数秒かかります。

| 状況 | 1ターンあたり | 内訳 |
|---|---|---|
| 検索できる記憶がまだ何も無い | 4回 | 通常回答・長期記憶の抽出・長期状態の抽出・作業記憶の抽出 |
| 通常（検索は不要と判断されたターンも含む） | 5回 | 検索プラン作成 + 上の4回 |
| 長期記憶の1回目の検索が0件 | 6回 | 上の5回 + 検索語の再生成 |

呼び出し回数は最適化していません。

| `data/working_memory.json` | 作業記憶の現在状態。現在の作業の Mission / Scope / Acceptance Criteria | 起動時に読み込み、存在する限り毎回すべて渡す |
| `data/working_memory_history.jsonl` | 作業記憶の変更履歴（add / replace / remove） | 毎回は渡さない。AI が必要と判断したターンにだけ読み込んで検索し、ヒットしたイベントだけを別枠で渡す |
| `data/long_term_memory_state.json` | 長期状態。ユーザーについての属性の現在値（subject / key / value） | 起動時に読み込んで検索対象にし、検索でヒットした項目だけを別枠で渡す |
| `data/long_term_memory_history.jsonl` | 長期状態の変更履歴（add / replace） | 毎回は渡さない。AI が必要と判断したターンにだけ読み込んで検索し、ヒットしたイベントだけを別枠で渡す |

### 会話原文（conversation.jsonl）

- 形式: JSONL。1行が1メッセージ（`{"role": "user", "content": "..."}`）
- 保存タイミング: AIの応答が正常に返るたびに、user / assistant の1ターンを追記する。`exit` / `quit` やエラーになったターンは保存しない
- 保存に失敗した場合は、応答を表示したうえでエラーを表示し、会話を続行する（そのターンは原文が残らないので、記憶抽出も行わない）

MVP2 で保存した `conversation.jsonl` はそのまま残りますが、そこから記憶を作り直すことはしません。記憶になるのは MVP3 以降で会話した発言だけです。

### 長期記憶（memories.jsonl）

- 形式: JSONL。1行が1つの記憶

  ```jsonl
  {"text": "ユーザーの名前はテスト太郎", "origin": "user", "evidence": "私の名前はテスト太郎です"}
  ```

  | フィールド | 内容 |
  |---|---|
  | `text` | 記憶内容 |
  | `origin` | 誰の発言が元か。現段階では常に `user` |
  | `evidence` | 根拠となった原文。元のユーザー発言からの抜き出し |

- 抽出タイミング: 通常の応答が返り、会話原文を保存できたあとに、そのユーザー発言1つだけを入力として、別の `claude -p` 呼び出しで抽出する。AIの発言や過去の会話は抽出の入力に含めない
- 「それに決めます」のように、その発言だけでは意味が確定しないものは記憶されない
- ファイルが壊れている場合（手で編集して不正なJSONLになったなど）は、該当の行番号を表示して起動を中止する。ファイルを修正するか削除する

記憶抽出はチャット本体より優先度が低いので、抽出の呼び出しが失敗した、不正なJSONが返った、`evidence` の検証に失敗した、保存に失敗した、のいずれの場合も `[警告]` を表示して会話を続行します。AIが返した `evidence` が元のユーザー発言にそのまま含まれていない場合、その候補は保存しません（AIが根拠を作り出していないことの確認）。

## 長期状態（構造化した Long-term Memory）

ユーザーについての属性を subject / key / value で持ち、現在値と変更履歴を分けて保存します。従来の長期記憶（`memories.jsonl`）とは別のレイヤーで、そちらは変更しません。

| 項目 | 意味 |
|---|---|
| `subject` | 誰についての情報か。現段階では `user` だけ |
| `key` | 何という属性か。AI が意味を判断して決める英語の snake_case（例: `favorite_fruit`） |
| `value` | その属性の現在の値。ユーザーの言葉のままの短い語句（例: `りんご`） |
| `evidence` | 根拠となったユーザー発言の抜き出し |

subject + key の組が「意味上の住所」で、1つの住所には現在値が1つだけあります。

MVP9 では、現在値（Current）とは別に、既存の値との関係がまだ確認できない発言を保留（Pending）として保存します。次は、現在値が `user.home_location = 川崎` のときの実際の表示です（実際の Claude でのスモークテストから。応答は省略）。

```text
あなた> 名古屋に住んでいます。
[長期保留] user.home_location: 名古屋（現在の値「川崎」は変更していません）
[長期保留の確認事項] 川崎にも今お住まいですか？（表示のみです。回答しても保留は自動では確定しません）

あなた> 川崎の家を引き払って、名古屋に引っ越しました。
[長期状態] user.home_location: 川崎 → 名古屋

あなた> 平日は名古屋、週末は川崎で暮らしています。
[長期状態] user.weekday_location: 名古屋

あなた> 今日は出張で名古屋に来ています。
（長期状態も保留も変わらない）
```

AI が replace と判断したのに、Python が置き換えの条件を確かめられなかった場合は、その理由も表示します。

```text
[長期保留] user.home_location: 名古屋（現在の値「川崎」は変更していません）
[長期保留の理由] AIの判断は replace でしたが、自動では反映しませんでした: old_value_evidence に既存の値「川崎」が含まれていません
[長期保留の確認事項] 川崎には今も住んでいますか？（表示のみです。回答しても保留は自動では確定しません）
```

MVP8 で `梨 → りんご` と置き換わっていた「最近は好きな果物はりんごです。」は、梨の終了を述べていないので、MVP9 では保留になります（意図した変更です）。

### 現在値（long_term_memory_state.json）

```json
{
  "items": [
    {
      "subject": "user",
      "key": "favorite_fruit",
      "value": "りんご",
      "evidence": "最近は好きな果物はりんごです",
      "updated_at": "2026-10-09T22:35:48+09:00"
    }
  ]
}
```

置き換えられた古い値（梨）は、このファイルには残りません。ファイルが壊れている場合（JSON でない、形式が違う、同じ subject + key が複数ある）は、エラーを表示して起動を中止します。保留を保存しても、このファイルは変わりません。

### 変更履歴（long_term_memory_history.jsonl）

追記のみで、1行が1つの変更です。

```jsonl
{"timestamp": "2026-10-09T22:35:26+09:00", "operation": "add", "subject": "user", "key": "favorite_fruit", "value": "梨", "evidence": "私の好きな果物は梨です"}
{"timestamp": "2026-10-09T22:35:48+09:00", "operation": "replace", "subject": "user", "key": "favorite_fruit", "old_value": "梨", "value": "りんご", "evidence": "最近は好きな果物はりんごです"}
```

`old_value` は replace のときだけあり、置き換えられる前の値です。`timestamp` は現在値の `updated_at` と同じ値で、作業記憶の変更履歴と同じ形式です。保留は履歴に入りません（履歴は現在値の変更の記録のまま）。

### 関係の判断（AI）

通常の応答が返り、会話原文を保存できたあとに、長期記憶の抽出とは別の `claude -p` 呼び出しで行います。MVP8 の構造化抽出の呼び出しを置き換えたもので、回数は増えていません。入力は現在の長期状態（subject / key / value の一覧）と今回のユーザー発言だけです。

```text
[long-term memory state]
- user.home_location: 川崎
[/long-term memory state]

[utterance]
今は名古屋に住んでいます。
```

AI は、発言に含まれるユーザー自身の長く有効な属性ごとに、既存の値との関係を判断して JSON 配列で返します。扱う属性が無ければ `[]` を返します。次は、スモークテストで実際に返った出力です。

```json
[{"decision": "pending", "subject": "user", "target_key": "home_location", "proposed_key": null, "proposed_value": "名古屋", "evidence": "今は名古屋に住んでいます。", "old_value_status": "not_stated", "old_value_evidence": null, "temporal_scope": "current", "reason": "現在名古屋に住んでいると述べていますが、既存の住まいである川崎から引っ越したのかどうかは明示されていません。…", "confirmation_question": "川崎にも今も住んでいますか？"}]
```

| decision | 意味 |
|---|---|
| `replace` | 既存の値が終わった・変わった・誤りだったと、発言が明確に示している |
| `coexist` | 既存の値を変えずに、新しい属性として追加できる（既存と両立する情報、または既存のどれとも関係しない新しい属性） |
| `pending` | 記憶する価値はあるが、既存の値が今も有効なのか置き換わったのかを発言だけでは判断できない |
| `no_change` | 状態を変える必要がない（一時的な状況、既存の値の再確認、過去の値だけの話など） |

| キー | 内容 |
|---|---|
| `target_key` | 関係する既存の key（同じ意味の属性があれば、その key をそのまま使う） |
| `proposed_key` / `proposed_value` | 新しい属性の key（coexist のとき）と、記憶する値（分からなければ null） |
| `evidence` | 根拠の部分。発言から一字一句そのまま抜き出す |
| `old_value_status` | 発言が既存の値について述べていること（`ended` / `wrong` / `continues` / `not_stated`） |
| `old_value_evidence` | replace のときだけ。既存の値が終わった・誤りだったことを述べた部分の、発言からの抜き出し |
| `temporal_scope` | いつのことか（`current` / `temporary` / `future` / `past`） |
| `reason` / `confirmation_question` | 判断理由と、確認の質問（pending のとき。replace のときも、自動で確定できない場合に備えて） |

AI への指示は事前実験の分類プロンプトをベースにし、MVP8 の抽出指示（扱う情報、key の再利用、形式、evidence）を統合しています。事前実験と同じく、指示の例に住まいの地名や期待する判断は載せていません。

### 状態遷移（Python）

AI の判断ごとに、Python が許された状態遷移だけを実行します。

| AI の判断 | Python の動作 |
|---|---|
| `replace` | 下の条件をすべて満たせば **replace**（現在値を置き換え、履歴に `old_value` つきの replace を残す）。満たさなければ **保留** |
| `coexist` | `proposed_key` が現在値に無ければ **add**（履歴に add を残す）。あれば上書きしない（同じ値なら何もしない、違う値なら **保留**） |
| `pending` | **保留**。現在値も履歴も変えない |
| `no_change` | 何もしない |

**replace を実行する条件**（すべて満たすときだけ）:

| 条件 | 何に基づくか |
|---|---|
| `target_key` が現在値にある | Python が確かめる事実 |
| `proposed_value` が空でない（現在値と同じなら何もしない） | Python が確かめる事実 |
| `proposed_value` が今回の発言にそのまま現れる（AI が作った値では置き換えない） | Python が確かめる事実 |
| `evidence` が今回の発言に一字一句含まれる | Python が確かめる事実 |
| `old_value_status` が `ended` か `wrong` | AI の自己申告（止める方向にだけ使う） |
| `temporal_scope` が `current` | AI の自己申告（止める方向にだけ使う） |
| `old_value_evidence` が今回の発言に一字一句含まれる | Python が確かめる事実 |
| `old_value_evidence` の中に、現在値（例: 川崎）がそのまま現れる | Python が確かめる事実 |
| `old_value_evidence` の中に、終了・変更・訂正を表す表現が現れる | Python が確かめる事実 |

終了・変更・訂正を表す表現は、属性の種類によらない15個の語幹だけです（`引き払` `引っ越` `転居` `退去` `離れ` `辞め` `やめ` `退職` `転職` `終わ` `変わ` `変え` `間違` `誤り` `訂正`）。これは意味の判定ではなく、「これが無ければ自動では置き換えない」という必要条件です。足りない言い方の更新は保留になるだけです。

これで止められる例と、止められない例があります。**この条件は完全な意味の検証ではありません。** Python が確かめているのは文字列が発言に現れるかどうかだけで、終了の語が否定されていないか、何が終わったのかは分かりません。

| 発言（現在値: 川崎）で AI が誤って replace と返した場合 | 結果 |
|---|---|
| 今は名古屋に住んでいます。／名古屋に住んでいます。 | 保留（川崎に触れていない） |
| 川崎にも住んでいますが、名古屋にも家があります。 | 保留（終了・訂正の表現が無い） |
| 単身赴任で、平日は名古屋に住んでいます。（MVP8 の誤置換） | 保留（川崎に触れていない） |
| 川崎の家は引き払っていません。（否定） | 保留（新しい値が発言に無い） |
| 川崎の職場を辞めました。（住まいではない） | 保留（新しい値が発言に無い） |
| 川崎の家は引き払っていません。名古屋にも部屋を借りました。 | **置き換わってしまう**（既知の限界） |
| 川崎の職場を辞めて、名古屋の会社に移りました。 | **置き換わってしまう**（既知の限界） |

最後の2つは、pytest に「既知の限界として失敗することを確かめるテスト」（`xfail(strict=True)`）として残しています。否定の語や「家」「職場」のような語を Python の一覧に足せば一部は止められますが、Python に意味を判定させることになるので、足していません。

逆に「横浜に引っ越しました。」のように既存の値に触れない正しい更新や、現在値「川崎市」に対する「川崎の家を引き払って」のような表記の違いは、自動では置き換えられず保留になります。

その他の検証は MVP8 と同じです（JSON 配列であること、`subject` が `user`、key の形式、`evidence` の原文一致、1つの発言で同じ key を2回変えないこと）。加えて、`decision` が4つのどれでもない要素は反映しません。

value が「同じ」かどうかは、英字の大文字小文字・全角半角・空白の違いだけを無視した完全一致で判定します。「りんご」と「リンゴ」が同じ意味か、value の内容が正しいかは、Python では判断しません。

現在値を保存してから履歴を追記し、保留は別のファイルへ保存します。抽出の呼び出しが失敗した、不正なJSONが返った、要素が検証を通らない、保存に失敗した、のいずれの場合も `[警告]` を表示して会話を続行します。現在値の保存に失敗したら履歴も書きません。履歴や保留の保存だけ失敗したら、現在値の変更は有効なままにします。

### 保留（long_term_memory_pending.json）

```json
{
  "items": [
    {
      "id": "p001",
      "subject": "user",
      "target_key": "home_location",
      "target_value": "川崎",
      "proposed_key": null,
      "proposed_value": "名古屋",
      "evidence": "今は名古屋に住んでいます。",
      "decision": "pending",
      "hold_reason": null,
      "reason": "現在名古屋に住んでいると述べていますが、既存の住まいである川崎から引っ越したのかどうかは明示されていません。…",
      "confirmation_question": "川崎にも今も住んでいますか？",
      "status": "unresolved",
      "created_at": "2026-10-14T22:45:36+09:00"
    }
  ]
}
```

| キー | 内容 |
|---|---|
| `target_key` / `target_value` | 関係する既存の key と、保留した時点のその値 |
| `proposed_key` / `proposed_value` | 発言が述べた属性と値（分からなければ null。例: 「引っ越しました。」） |
| `decision` / `hold_reason` | AI の元の判断と、Python が格下げした理由（AI 自身が pending を選んだときは null） |
| `confirmation_question` | 確認の質問。格下げした replace に質問が無ければ、Python が「以前の「川崎」は今も有効ですか？」を入れる |
| `status` | 常に `unresolved`。確定・削除・期限切れの処理はまだ無い |

- **Current と Pending の違い**: Current は確定した現在の値です。Pending は、ユーザーがそう述べたという事実の記録で、既存の値との関係がまだ確認できていないものです。Pending を保存しても Current は変わらず、Current が無効になることもありません
- subject・target_key・proposed_key・proposed_value・evidence が同じ保留（英字の大文字小文字・全角半角・空白の違いは無視）は、2回目以降は保存しません。AI の理由や質問の言い回しの違いは見ません
- ファイルが無ければ0件として起動します。壊れていれば、エラーを表示して起動を中止します

### JSON 形式の崩れへの対応

関係判断の出力の前に、`<reasoning>` などの推論文が漏れることがあります（事前実験の121回中7回）。通常の解析に失敗したときだけ、出力から JSON を取り出します。

- `{` か `[` から始まり、それ自体で完結する JSON の値を探し、**ちょうど1つで、出力の末尾にある**ときだけ使う
- 0個、2個以上、後ろに別の文がある場合は失敗にする（どれかを選ぶことも、途中を直すこともしない）
- 取り出した JSON にも、すべての検証と replace の条件を適用する
- 取り出したときは `[警告] 長期状態の抽出結果にJSON以外の前置きがあったため、末尾のJSONだけを解析しました` を表示する（回数を数えられるように）
- 対象は関係判断の出力だけで、検索プランや作業記憶の抽出は MVP8 までと同じ

## 記憶の検索

通常回答の前に、次の流れで記憶を検索します。検索できる記憶は、長期記憶（従来の記憶と長期状態の現在値・保留）、長期状態の変更履歴、作業記憶の変更履歴の3種類です。

```text
検索プラン作成（AI） → 作業記憶の変更履歴の検索（Python。プランで必要とされたときだけ、1回）
                    → 長期状態の変更履歴の検索（Python。プランで必要とされたときだけ、1回）
                    → 長期記憶の検索（Python。プランで必要とされたときだけ。従来の記憶と現在値・保留を同じ検索語で検索する）
                         → どれかにヒットあり → 関係する保留の選択（Python） → 回答（AI）
                         → どれも0件 → 検索語を再生成（AI） → 再検索（Python） → 回答（AI）
```

### 検索プラン（AI）

現在の作業記憶と現在のユーザー発言を別の `claude -p` 呼び出しへ渡し、長期記憶が必要か、長期状態の変更履歴が必要か、作業記憶の変更履歴が必要かをそれぞれ判断させ、必要なものについて検索語を最大3個ずつ、JSONで返させます。どの記憶を検索するか・検索語を何にするかを、Pythonのルールで決めることはしません。

```json
{
  "needs_memory": true,
  "queries": ["果物", "フルーツ", "favorite_fruit"],
  "needs_long_term_memory_history": true,
  "memory_history_queries": ["favorite_fruit", "果物", "フルーツ"],
  "needs_working_memory_history": false,
  "history_queries": []
}
```

| キー | 内容 |
|---|---|
| `needs_memory` / `queries` | 長期記憶（従来の記憶と長期状態の現在値）が必要か、その検索語 |
| `needs_long_term_memory_history` / `memory_history_queries` | 長期状態の変更履歴が必要か、その検索語（MVP8） |
| `needs_working_memory_history` / `history_queries` | 作業記憶の変更履歴が必要か、その検索語（MVP7） |

- 作業記憶を渡すのは、「現在状態だけで答えられる質問か、過去の変更を見る必要があるか」を判断できるようにするためです。変更履歴そのもの、長期記憶の中身、長期状態の中身は渡しません
- 検索プランナーには、長期状態の key が英語の snake_case であること、value と evidence はユーザーの言葉のままであることを説明しています。上の例のように、AI は日本語の語と、ありそうな key の両方を検索語にします
- 変更履歴のキーが無い出力（MVP4・MVP7 形式）は、その変更履歴は不要として扱います
- 長期記憶の1回目の検索が、従来の記憶も現在値も0件だったときだけ、同じ入力に0件だった検索語を足して、別の検索語を考えさせます。変更履歴は再検索しません（2回目のプランに含まれる変更履歴の指定は使いません）

### 作業記憶の変更履歴の検索（Python）

`working_memory_history.jsonl` をそのターンに読み込み、単純に文字列検索します。

- 検索対象は各イベントの `operation` / `field` / `text` / `target` / `evidence`。`timestamp` は検索しないが、結果には含める
- ヒットの判定とスコアは長期記憶の検索と同じ（1つの検索語の中は AND、検索語どうしは OR、英字の大文字小文字と全角・半角はそろえる）
- 上限は10件。超える場合はスコアの高い順、同点なら新しいイベントを残す
- 選んだイベントは、最後に古い順（時刻順）へ並べ直して渡す
- 履歴ファイルが無い、または0件でも会話は続ける。履歴ブロックなしで回答へ進む

### 長期状態の検索（Python）

現在値（`long_term_memory_state.json`）と変更履歴（`long_term_memory_history.jsonl`）に対する単純な文字列検索です。ヒットの判定とスコアは、下の長期記憶の検索と同じです。

| | 検索対象 | 上限 | 並び |
|---|---|---|---|
| 現在値 | `subject` / `key` / `value` / `evidence` | 5件 | スコアの高い順、同点は保存順 |
| 変更履歴 | `operation` / `subject` / `key` / `value` / `old_value` / `evidence` | 10件（超えたらスコアの高い順、同点は新しい順に残す） | 選んだあとで古い順 |

- 現在値は、従来の記憶と同じ検索語（`queries`）で検索する。現在値の全項目を毎回渡すことはしない
- `updated_at` と `timestamp` は検索しないが、結果には含める
- 履歴ファイルが無い、または0件でも会話は続ける。履歴ブロックなしで回答へ進む

保留（MVP9）は、毎回すべては渡しません。長期記憶の検索をしたターンにだけ、次の2つを合わせて最大5件を渡します。Claude の呼び出しは増えません。

- 現在値の検索でヒットした項目の key と、`target_key` か `proposed_key` が同じ保留（例: `home_location` の現在値がヒットしたら、`home_location` についての保留）。多すぎる場合は新しく保存されたものを残す
- 同じ検索語でヒットした保留（検索対象は `subject` / `target_key` / `target_value` / `proposed_key` / `proposed_value` / `evidence`）

従来の記憶と現在値が0件でも、保留がヒットすれば再検索しません。保留を検索したターンにだけ、次のように表示します。

```text
[検索] 住 / 引っ越 / residence
[検索結果] 2件
[長期保留検索] home_location / 住 / 引っ越 / residence
[長期保留検索結果] 1件
```

`[長期保留検索]` は、つながりを見た現在値の key と、使った検索語です。`[検索結果]` の件数は MVP8 と同じく従来の記憶と現在値の合計で、保留は含めません。「1+1は？」のように長期記憶が不要と AI が判断したターンでは、保留も検索しません。

### 長期記憶の検索（Python）

`memories.jsonl` に対する単純な文字列検索です。

- 検索対象は各記憶の `text` と `evidence`
- 1つの検索語は空白区切りのキーワードで、キーワードをすべて含む記憶がヒットする。複数の検索語はどれか1つにヒットすればよい
- ヒットした検索語のキーワード数の合計をスコアにして、上位5件までを返す
- 英字の大文字小文字と全角・半角の違いだけはそろえる。読み・同義語・言い換えは考慮しない

言い換えや表記ゆれは検索側では吸収せず、AIが別の検索語を出すことに任せています。

### AIとPythonの役割分担

| 担当 | やること |
|---|---|
| AI | 長期記憶・長期状態の変更履歴・作業記憶の変更履歴のどれが必要かの判断、検索語を考える、長期記憶が0件なら別の検索語を考える、検索結果を使って回答する（現在状態と取得したイベントから過去の状態を読み取ることを含む）。記憶抽出では、発言に後で役立ちそうな記憶があるかの意味判断 |
| Python | 記憶の読み込みと保存、検索プランや抽出結果のJSON検証、`evidence` の検証、`origin` の付与、検索実行、スコアリング、最大件数、変更履歴の時系列への並べ替え、同じ検索語の重複排除、検索ラウンドの上限、回答用の Claude へ渡す記憶の制御 |

検索はチャット本体より優先度が低いので、検索プランの呼び出しが失敗した、不正なJSONが返った、のいずれの場合も `[警告]` を表示し、長期記憶も変更履歴も検索せずに回答へ進みます。変更履歴のファイルが壊れていて読めない場合も `[警告]` を表示し、履歴なしで回答へ進みます。長期記憶も長期状態も変更履歴もまだ1件も無いときは、検索プランの呼び出し自体をしません。

## 作業記憶（Working Memory）

現在進行中の作業について、作業が終わるまで忘れてはいけない情報を置く場所です。長期記憶とは役割が違います。

| | Long-term Memory | Working Memory |
|---|---|---|
| ファイル | `data/memories.jsonl` | `data/working_memory.json` |
| 中身 | 過去のユーザー発言から抽出した記憶全般。過去の経緯を含む | 現在の作業の Mission / Scope / Acceptance Criteria だけ。現在有効な状態 |
| Claude への渡し方 | AI が検索語を考え、ヒットしたものだけ渡す | 存在する限り、毎回すべて渡す |
| 変更 | 追記のみ | add / replace / remove（変更履歴は別ファイルに追記） |
| 両者が矛盾したとき | | こちらを優先する |

### 保存形式

フィールドは `mission`（作業の目的）/ `scope`（対象範囲）/ `acceptance_criteria`（完了条件）の3つだけです。各項目は内容と、根拠となったユーザー発言の抜き出しを持ちます。

```json
{
  "mission": [
    {"text": "3環境へ展開できる資産を作る", "evidence": "3環境へ展開できる資産を作ります"}
  ],
  "scope": [
    {"text": "商用環境", "evidence": "商用環境"},
    {"text": "検証環境", "evidence": "検証環境"},
    {"text": "開発環境", "evidence": "開発環境"}
  ],
  "acceptance_criteria": [
    {"text": "3環境すべての資産が揃っていること", "evidence": "3環境すべての資産が揃えば完了です"}
  ]
}
```

ファイルが壊れている場合は、エラーを表示して起動を中止します。ファイルを修正するか削除してください。

### 抽出（AI）と検証・保存（Python）

通常の応答が返り、会話原文を保存できたあとに、長期記憶の抽出とは別の `claude -p` 呼び出しで行います。入力は現在の作業記憶と今回のユーザー発言だけで、AIの発言や過去の会話は含めません。

AIは、候補ごとに `operation`（add / replace / remove）を付けたJSON配列を提案するだけです。雑談・質問・進捗の報告・個々の手順の指示は対象外としています。

```json
[
  {"operation": "add", "field": "scope", "text": "商用環境を対象とする", "evidence": "商用環境を対象にします"},
  {"operation": "replace", "field": "scope", "target": "検証環境を対象とする", "text": "ステージング環境を対象とする", "evidence": "検証環境の代わりにステージング環境を対象にします"},
  {"operation": "remove", "field": "scope", "target": "ステージング環境を対象とする", "evidence": "ステージング環境はやっぱり対象外にします"}
]
```

- add: 新しい項目を追加する
- replace: 既存の項目1つ（`target`）を別の内容（`text`）に置き換える
- remove: 既存の項目1つ（`target`）を取り除く。「Xは対象外」「Xは不要」「Xを外す」は、否定文を追加するのではなく remove で表す

`target` には、現在の作業記憶にある項目の文面をそのまま書かせます。MVP5 形式（`operation` なし、置き換えは `replaces`）も受け付け、内部で add / replace に読み替えます。

Pythonは次を確認し、通った候補だけを反映します。

- `operation` が add / replace / remove のいずれかである
- `field` が3つのフィールドのいずれかである
- `evidence` が今回のユーザー発言にそのまま含まれている
- add / replace: `text` が空でなく、同じフィールドに同じ内容の項目がまだ無い
- replace / remove: `target` が同じフィールドに実在する項目と一致し、一致する項目がちょうど1つである

`target` の一致は、英字の大文字小文字・全角半角・前後や連続する空白の違いだけを無視した完全一致です。部分一致や似た項目では変更しません（target が「ステージング環境」なら「ステージング環境を対象とする」は消さない）。

抽出の呼び出しが失敗した、不正なJSONが返った、候補が検証を通らない、保存に失敗した、のいずれの場合も `[警告]` を表示して会話を続行します。

### 変更履歴（working_memory_history.jsonl）

現在状態から削除しても「以前は対象だった」ことが失われないよう、作業記憶への変更を現在状態とは別のファイルへ1行1イベントで追記します。

```jsonl
{"timestamp": "2026-10-07T17:34:05+09:00", "operation": "add", "field": "scope", "text": "検証環境", "evidence": "商用環境、検証環境、開発環境の3環境を対象にします"}
{"timestamp": "2026-10-07T17:34:26+09:00", "operation": "replace", "field": "scope", "target": "検証環境", "text": "ステージング環境", "evidence": "検証環境の代わりにステージング環境を対象にします。"}
{"timestamp": "2026-10-07T17:34:51+09:00", "operation": "remove", "field": "scope", "text": "ステージング環境", "evidence": "ステージング環境はやっぱり対象外にします。"}
```

| フィールド | 内容 |
|---|---|
| `timestamp` | 変更を反映した時刻（ローカル時刻） |
| `operation` | add / replace / remove |
| `field` | mission / scope / acceptance_criteria |
| `text` | add は追加した項目、replace は置き換え後の項目、remove は削除した項目 |
| `target` | replace のときだけ。置き換え前の項目 |
| `evidence` | 根拠となったユーザー発言の抜き出し |

- 現在状態（`working_memory.json`）を保存してから履歴を追記する。現在状態の保存に失敗したら履歴も書かない。履歴の追記だけ失敗したら `[警告]` を表示し、現在状態の変更は有効なままにする
- 履歴は毎回は渡さない。AI が必要と判断したターンにだけ検索し、ヒットしたイベントだけを渡す（「記憶の検索」を参照）。現在状態を履歴から作り直すことはしない
- MVP6 より前に作られた項目には add のイベントが無い

## Claudeへ渡すもの

通常回答のたびに、次の順で渡します。過去の `conversation.jsonl` 全文、`memories.jsonl` 全件、長期状態の全項目、2つの変更履歴の全文は渡しません。

1. 作業記憶（存在する限り常に、全項目）
2. 今回の検索でヒットした作業記憶の変更履歴（最大10件、古い順。検索しなかった・0件だったターンではブロックごと省く）
3. 今回の検索でヒットした長期状態の現在値（最大5件）
4. 今回の検索で選んだ長期状態の保留（最大5件、保存順。MVP9。無ければブロックごと省く）
5. 今回の検索でヒットした長期状態の変更履歴（最大10件、古い順。検索しなかった・0件だったターンではブロックごと省く）
6. 今回の検索でヒットした従来の長期記憶（最大5件）
7. 今回起動してからの会話
8. 現在のユーザー入力

作業についてのもの（1・2）と、ユーザーについてのもの（3〜6）をそれぞれまとめ、どちらも「現在状態 → 変更履歴」の順に並べています。保留のブロックは次の形です（スモークテストで実際に渡したもの）。

```text
[long-term memory state]
- user.home_location: 川崎 (evidence: 今は川崎に住んでいます。, updated_at: 2026-10-01T09:00:00+09:00)
[/long-term memory state]

[long-term memory pending]
- p001 (created_at: 2026-10-14T22:45:36+09:00)
  subject: user
  target_key: home_location
  target_value: 川崎
  proposed_value: 名古屋
  evidence: 今は名古屋に住んでいます。
[/long-term memory pending]

[retrieved memories]
- ユーザーは現在名古屋に住んでいる (origin: user, evidence: 今は名古屋に住んでいます。)
[/retrieved memories]

[user]
今の住まいは？
```

保留の確認質問・判断理由は回答用の Claude へは渡しません。長期状態と変更履歴のブロックは次の形です。

```text
[long-term memory state]
- user.favorite_fruit: りんご (evidence: 最近は好きな果物はりんごです, updated_at: 2026-10-09T22:35:48+09:00)
[/long-term memory state]

[long-term memory history]
- 2026-10-09T22:35:26+09:00
  operation: add
  subject: user
  key: favorite_fruit
  value: 梨
  evidence: 私の好きな果物は梨です

- 2026-10-09T22:35:48+09:00
  operation: replace
  subject: user
  key: favorite_fruit
  old_value: 梨
  value: りんご
  evidence: 最近は好きな果物はりんごです
[/long-term memory history]

[retrieved memories]
- ユーザーの好きな果物は梨 (origin: user, evidence: 私の好きな果物は梨です。)
- ユーザーが最近好きな果物はりんご (origin: user, evidence: 最近は好きな果物はりんごです)
[/retrieved memories]

[user]
前に好きだった果物は？
```

作業記憶まで含めた例:

```text
[working memory]
Mission:
- 3環境へ展開できる資産を作る

Scope:
- 商用環境
- 検証環境
- 開発環境

Acceptance Criteria:
- 3環境すべての資産が揃っていること
[/working memory]

[working memory history]
- 2026-10-07T18:48:19+09:00
  operation: replace
  field: scope
  target: 検証環境
  text: ステージング環境
  evidence: 検証環境の代わりにステージング環境を対象にします。

- 2026-10-07T18:48:45+09:00
  operation: remove
  field: scope
  text: ステージング環境
  evidence: ステージング環境はやっぱり対象外にします。
[/working memory history]

[retrieved memories]
- ユーザーの名前はテスト太郎 (origin: user, evidence: 私の名前はテスト太郎です)
[/retrieved memories]

[user]
私の名前と、ステージング環境を外した時刻は？
```

システム指示で、作業記憶は「現在の作業で継続的に守る必要がある条件である」「作業が完了したか、成果物に不足がないかは、必ずこれを基準に判断する」「現在の発言で明示的に変更された場合は現在の発言を優先する」と伝えています。MVP6 で、作業記憶は「現在有効な作業状態で、対象外にした・取り消した項目は取り除かれている」「項目どうしが矛盾していたら勝手に合わせず指摘する」も伝えるようにしました。

検索で取得した記憶については、「検索で取得した過去の記憶であり、現在の会話の履歴ではない」「保存されている記憶の全部ではない」「必要な場合にだけ使う」「現在の発言と矛盾したら現在の発言を優先する」「必要な情報が見当たらなければ推測せず、覚えていないと伝える」と伝えています。MVP6 で、「取得した記憶には後で変更・取り消しされた過去の経緯が含まれることがある」「作業記憶と矛盾したら作業記憶を現在の状態として優先する」も伝えるようにしました。

MVP7 で、作業記憶の変更履歴については、「過去の変更イベントを検索で取得したもので、古い順に並んでいる」「過去に起きた状態変更の記録であって、現在の状態ではない。イベントにある値を現在の対象や条件として扱わない」「現在の状態については常に作業記憶を優先する」「過去の状態・変更の理由・変更の日時については履歴を根拠にし、履歴から読み取れることは推定としてではなく履歴を根拠として答える」「検索で見つかったイベントだけで全部ではないので、ブロックに無い出来事を補わない」「必要なイベントが見当たらなければ、推測せず、履歴からは確認できないと伝える」と伝えるようにしました。`timestamp` は保存されている値をそのまま渡します。

MVP8 で、長期状態については次のように伝えるようにしました。優先順位は、現在の会話でのユーザー発言 → 現在状態（作業については作業記憶、ユーザーについては長期状態の現在値）→ 従来の長期記憶、です。変更履歴は過去を答えるための根拠で、現在値としては使いません。

- `[long-term memory state]` は、ユーザーについて現在有効な値である。現在の会話でユーザーが別の値を述べた場合は、現在の発言を優先する
- `[retrieved memories]`（従来の記憶）は発言から抽出した記憶を追記しただけの記録で、値が変わる前の古い情報が混ざっていることがある。`[long-term memory state]` と矛盾したら、`[long-term memory state]` を現在の値として優先する
- `[long-term memory history]` は過去の値の変更の記録で、現在の値ではない。`old_value` や、後のイベントで置き換えられた value を現在の値として扱わない
- 以前の値や、値が変わった時期については、`[long-term memory history]` を根拠にし、推定としてではなく履歴を根拠として答える。そこに無い変更を補わない。必要なイベントが見当たらなければ、履歴からは確認できないと伝える

MVP9 で、保留については次のように伝えるようにしました。

- `[long-term memory pending]` は、ユーザーについての新しい発言のうち、既存の値との関係（置き換わったのか、両立するのか）がまだ確認できないため、`[long-term memory state]` を変えずに保留しているもの
- 保留は、ユーザーがそう述べたという事実の記録で、発言が疑わしいという意味ではない。多くの場合、現在値より後に述べられたもので、古い情報・重要度の低い情報として無視しない
- 関係する保留があるときは、`[long-term memory state]` の値だけで断定しない
- 保留の値を、確定した現在の値として扱わない。保留があることだけを理由に、現在値を無効になったものとして扱わない
- 関係する保留があるときは、ユーザーが新しく述べたこと（保留の evidence）、以前から記録されている値、両者の関係が未確認であること、の3つを区別して伝える。保留の内容はユーザー自身の発言として伝え（「〜と伺っています」）、以前の値を確かな情報として先に強調しない。ただし、保留を常に現在値より優先するわけではない
- 関係を説明するために、発言に無い生活の事情（理由、家族、仕事、住まい方など）を推測して補わない。例としても挙げない
- 保留を確認して記録を確定・更新する機能はまだ無いので、「答えれば記録を更新する」といった約束をしない。未確定な関係を説明するところまでにする
- `[retrieved memories]` に保留と同じ内容があっても、それだけで確定した値として扱わない

最初のスモークテストでは、「今の住まいは？」に「確定している記録では**川崎**です」と古い現在値から答え始め、「たとえば単身赴任などで」と発言に無い事情を例に挙げ、「教えていただければ記録を正しく更新します」と実装していない処理を約束しました。そこで上の3つの指示を足しました。修正後に独立して3回聞いたときの回答の1つです。

```text
AI> 最近、「今は名古屋に住んでいます」と伺っています。以前の記録では、お住まいは川崎となっています（2026年10月1日時点）。

この2つの関係はまだ確認できていないため、今のお住まいがどちらかは断定できません。
```

3回とも、推測と約束は無くなりました。ただし3回とも「どちらが今の住まいかは断定できない」と、名古屋か川崎かの二者択一として説明していました。未確認なのは「川崎が今も残っているか」です。

## 現段階の限界

- replace の条件は完全な意味の検証ではない。AI が replace を誤り、かつ新しい値が発言にあり、抜き出しが条件を満たす場合（否定「川崎の家は引き払っていません。名古屋にも部屋を借りました。」、別のものの終了「川崎の職場を辞めて、名古屋の会社に移りました。」、発言全体を抜き出したときなど）は上書きされる
- 逆に、既存の値に触れない正しい更新（「横浜に引っ越しました。」）、表記の違い（現在値「川崎市」と発言「川崎」）、15個の表現に無い言い方（「最近は好きな果物はりんごです。」）は、自動では置き換えられず保留になる
- 保留は確定・削除・期限切れの処理が無く、溜まっていく。確認質問を表示しても、ユーザーの回答から保留を確定する処理は無い。回答は通常の発言として改めて判断されるだけで、「はい」のような短い答えでは何も変わらない
- 回答用の Claude は、保留があるときに「名古屋か川崎か、どちらが今の住まいかは断定できない」と二者択一で説明しがちである（修正後の3回すべて）。両方が有効な可能性もあり、未確認なのは以前の値が今も有効かどうかである
- 新しい値は発言にそのまま現れなければ置き換えないので、AI が値を言い換えた場合（発言「名古屋」に対して値「名古屋市」）は保留になる
- coexist は既存の値を消さないが、既存の値が今も有効であると確認したわけではない
- AI が誤って no_change にした新しい情報は、長期状態にも保留にも残らない（従来の長期記憶と会話原文には残る）
- 予定（「来月引っ越す予定」）は coexist で別の key になることがあり、期日が過ぎても古いまま残る
- JSON の取り出しは関係判断の出力だけ。作業記憶の抽出でも同じように推論文が漏れて失敗することがある（スモークテストで1回確認）
- 事前実験とスモークテストは住まいの話題だけで、長期状態の項目も1つだけだった

- 長期状態に入るのは、MVP8 以降の発言だけ。それより前に `memories.jsonl` へ保存された記憶は移行していないので、現在値も履歴も無い
- 長期状態の key は AI が決めるので、同じ意味の属性に別の key が付く可能性がある（key の揺れ）。その場合は別の項目として追加され、古い値が現在値として残る。key の統合・辞書・類似度による判定は無い
- 1つの subject + key に持てる値は1つだけ。「梨も好き」のように値を足す発言は、MVP9 では別の key（coexist）か保留になる
- 更新（好みが変わった）と訂正（言い間違いだった）を状態遷移では区別しない。AI は `old_value_status` で `ended` / `wrong` を区別して返すが、どちらも replace として履歴に残る
- 長期状態から項目を消す手段が無い（「もう好きではない」と言っても現在値は残る）
- subject は `user` だけ。他の人・物・プロジェクトについての情報は、従来の長期記憶にしか入らない
- 同じ内容が `memories.jsonl` と長期状態の両方に保存される。重複排除はしていない
- `memories.jsonl` には古い値が残り続け、検索でヒットすれば回答用の Claude にも渡る。現在値を優先するよう指示しているだけで、取り除いてはいない
- 長期状態の検索は部分一致だけ。key は英語、value と evidence はユーザーの言葉なので、AI が出した検索語がどちらにも現れなければ見つからない
- 長期状態の変更履歴の検索は1ターンに1回だけで、0件でも再検索しない。上限は10件

- 作業記憶はタスク管理ではない。進捗、次にやること、完了の判定、複数の作業、作業の切り替えは扱わない。作業を終えたら `data/working_memory.json` を手で削除する必要があり、消さない限り古い作業の条件が渡され続ける
- 作業記憶の項目を消せるのは、ユーザーが明示的に外したときだけ。AI が `target` を既存の文面どおりに書けなかった場合は消えない（警告が出るだけ）
- scope を変えても完了条件は連動して変わらない。食い違いの解消はユーザーが改めて指示する必要がある（AI は指摘はする）
- 過去のある時点の作業状態は、Python では再構築しない。現在状態と検索でヒットしたイベントから AI が読み取るだけなので、必要なイベントが検索に漏れると、誤った過去状態を答える余地がある
- 変更履歴の検索は1ターンに1回だけで、0件でも検索語を変えて再検索しない
- 変更履歴の検索結果は最大10件で、超えた分は（同点なら古いものから）落ちる。履歴が長くなると「最初はどうだったか」に必要なイベントが届かないことがある。逆に履歴が短いうちは、`scope` や「環境」のような広い検索語でほぼ全件がヒットし、絞り込みにはなっていない
- 同じ発言から生まれた複数のイベントは同じ `evidence` を持つので、`evidence` 経由で無関係な項目のイベントもヒットする
- MVP6 より前に作られた項目には履歴が無い。過去のデータからの補完（backfill）はしていない
- 変更履歴は時刻を持つが、長期記憶と会話原文には時刻が無いので、履歴のイベントと長期記憶の前後関係は分からない
- 長期記憶には取り消された古い内容も残り続ける（superseded・削除は無い）。作業記憶を優先するよう指示しているだけ
- 作業記憶は毎回すべて渡すので、項目が増えるほど入力が増える。件数の上限は設けていない
- 作業の前提は長期記憶にも同じ内容が抽出されるため、2つのファイルに重複して残る
- 何を作業記憶に入れるかはAIの判断で、同じ発言でも結果が変わりうる
- 検索は部分一致だけなので、記憶の文面に現れない言葉で聞くと見つからない。例: 「ユーザーはヴェゼルに乗る予定である」という記憶は、「車は何に乗る予定だっけ？」では見つからない（記憶に「車」という語が無く、AIは答えである「ヴェゼル」を検索語にできない）
- 検索語を考えるAIには現在の発言と作業記憶しか渡さないため、「それは何インチ？」のように今の会話の流れに依存する質問では、適切な検索語を作れない
- `memories.jsonl` の記憶は追記のみ。更新・取り消し・矛盾解消はなく、名前を言い直すと新旧両方の記憶が残る
- 重複排除は `text` の完全一致だけ
- 記憶に日時がないため、「今回の」のような相対的な表現がいつのことか分からなくなる
- 1ターンあたり Claude Code を4〜6回呼び出す（通常5回。最適化していない）
- `claude` コマンドは、ログイン中のアカウントのメールアドレスと今日の日付を自動でモデルへ渡す。そのため、記憶以外の経路でユーザーに関する情報がAIに届くことがある

## テスト

```powershell
python -m pytest
```

テストは `subprocess` / Claude をモックして実行するため、`claude` を起動せず、利用枠も消費しません。保存先には pytest の一時ディレクトリを使うため、`data/` にも触れません。
